# 知らせ

関所（`sentinel`）が、いつもと違うことを本人に知らせる形を決める。何を知らせるか、「初めて見る」の覚えを記録と別に持つこと、natsumi と運用の係に頼らない道で届けることは ADR-0006 の Decision「いつもと違うことを知らせる」が決め、組の細かな取り方・まとめの形・届ける道の作りをこの文書（と実装）に委ねている。

## 何を知らせるか

| 知らせ | いつ |
|---|---|
| 初めて見る組（`first-seen`） | 組を初めて見たとき、1 件ずつ |
| 本人の答え（`answer`） | 承認待ちへの答えと許しの取り消しを受け、台帳に効いたとき、1 件ずつ |
| 1 日のまとめ（`daily-summary`） | 1 日 1 回、決めた時刻に |

## 初めて見る組

関所は、書き終えた記録を 1 件ずつ見て、次の組を取り出す。

| 組（`pair`） | 取り出す記録 | 組の中身（`key`） |
|---|---|---|
| `destination` | 開く宛先へ通した要求（`kind` が `http`、`verdict` が `allow`） | 宛先の名前 |
| `operation` | 開く宛先へ通した書きの要求（GET・HEAD・OPTIONS・TRACE 以外）で、操作の名前のあるもの | 名前・操作の名前・対象を空白でつないだもの（対象が無ければ名前と操作の名前） |
| `write` | 開く宛先へ通した書きの要求で、生の操作のもの（操作の名前が無い） | 名前・method・path を空白でつないだもの |
| `passthrough` | passthrough でつないだ接続 | 元の宛先の IP とポート |
| `denied-name` | 名前解決で断った問い合わせ（`kind` が `dns`、`verdict` が `deny`）。振り分けにある名前に search の接尾辞を付けただけの問い合わせは除く（下） | 問い合わせた名前 |

- 書きの組は、記録に操作の名前があれば操作と対象で、無ければ（生の操作）名前・method・path で取る。query はどちらにも入れない。
- 操作の組の細かさは、期限付きの許しと同じ「操作 × 対象」である（[振り分けの形式](routes.md) の「rules」）。規則が対象をリポジトリまでにしていれば、issue や PR の番号が違っても 1 つの組になる。対象を省いた規則は path の引数すべてが対象になるので、番号ごとに別の組になる。
- 生の操作の組は、path に番号が入れば番号ごとに別の組になる。規則で操作に名前を付ければ減る。
- 許しに当たって通った書きも、ほかの書きと同じに組になる。承認待ちにした要求（`ask`）、先に頼んだこと（`agent`）、本人の答え（`answer`）は組にしない。
- 断った要求と接続、振り分けの読み直し、関所自身の要求は組にしない。断ったものは 1 日のまとめに出る。
- 名前解決の問い合わせは、通した名前を組にしない。通した名前は、その名前への要求が `destination` の組になる。
- 作業環境の名前解決が search の接尾辞を付けて引いた名前のうち、接尾辞を 1 つ除くと振り分けにある名前になるもの（記録の理由が「a name in the table with a search suffix added」、[関所の記録](audit.md) の「名前解決の記録の理由」）は、組にしない。道具がふつうに名前を引くたびに、接尾辞の数だけ初めての名前が出るのを避けるためである。記録には残り、1 日のまとめの「断ったもの」にも出る。
- 接尾辞を除いても振り分けに無い名前は、ほかの断った名前と同じに組にする。接尾辞を付けた形の問い合わせも、そのまま問い合わせた名前で組になる。

### 覚え

- 見た組は、関所の SQLite のファイルの表 `seen` に、初めて見た記録の時刻と番号とともに残す（[関所の記録](audit.md) の「置き場所」）。
- この表は記録と別に持ち、古い記録を消すときにも消さない。記録の期間が過ぎても、一度見た組は「初めて」にならない。
- 表が空のうちは、何もかもが初めてなので知らせが多い（ADR-0006 の Consequences）。

### 前に覚えた組との続き方

操作の組（`operation`）は、書きの組を名前・method・path で取っていた版の後に足した。

- 生の操作の書きは、前と同じ組の種類（`write`）と中身で取る。前に覚えた組は、そのまま「見たことのある組」として効く。
- 操作の名前のある書きは、新しい組の種類（`operation`）で取る。前の版がその書きを `write` の組として覚えていても、`operation` の組としては初めてなので、操作 × 対象ごとに 1 度だけ、もう 1 度知らせる。
- 前の版が覚えた `write` の組のうち、いまは操作の名前の付く書きのものは、表に残るが引かれない。消さない（覚えは記録と別に持ち、消さない、という決まりのとおり）。

## 1 日のまとめ

- 関所は、`-summary-at`（`HH:MM`、既定 `00:00`）の時刻に、`-summary-timezone`（IANA の名前、既定 `UTC`）で、まとめを作る。まとめが扱うのは、前の日の同じ時刻から、その時刻までの記録である。
- その時刻に関所が動いていなければ、その日のまとめは後から作らない。

まとめには、次の 5 つを書く。

| 部分 | 中身 |
|---|---|
| 書きの件数 | 開く宛先へ通した書きの要求の件数を、宛先と操作ごとに、多い順に。生の操作は宛先と method ごと |
| 新しく現れた組 | その期間に初めて見た組（上の表の組と中身）を、古い順に |
| 本人に聞いたもの | `verdict` が `ask` の記録（承認待ちにした要求と、作業環境が先に頼んだこと）を、件数の多い順に |
| 断ったもの | `verdict` が `deny` の記録を、件数の多い順に。開く宛先へ張られたまま何も送られずに閉じた接続（[関所の記録](audit.md) の「接続の記録」）は断ったものではないので入らない |
| 本人の答え | `kind` が `answer` の記録（許した・断った答えと、許しの取り消し）を 1 件ずつ、古い順に |

- 聞いたものと断ったものは、種類・宛先・理由が同じで、操作の名前のあるものは操作と対象が、生の操作は method と path が同じものを 1 行にまとめる。書きの組と同じく、操作のある要求は番号ごとに行が分かれない。承認待ちにした要求の理由には承認待ちの id が入るので、同じ承認待ちにまとめた要求が 1 行になる。
- 本人の答えの行は、時刻・向け直し元・許した（`allowed`）か断った（`denied`）か取り消した（`revoked`）か・承認待ちか許しの id・宛先と操作と対象（生の操作は method と path）である。許した答えには、記録の理由（選んだ選択肢とその文）を足す。取り消しの理由は書かない。1 回の許しの取り消しの理由には、要求の query が入りうるためである。
- 各部分は 30 行までで、残りは件数だけを書く。
- 聞いたものと断ったものには、振り分けの読み直しと、関所自身の要求と、本人の答えは入れない。断った答えと取り消しは、本人の答えの部分にだけ出る。

## 本人の答え

関所は server の答えを信じる（ADR-0001）。server が本人の答えを偽っても、本人が natsumi の外の道で気づけるように、受けた答えを 1 件ずつ知らせる（ADR-0006）。

- 知らせるのは、本人の口（[承認の口](approvals-api.md)）で受けた答えと取り消しのうち、記録に書けて台帳に効いたものである。記録に書けずに受けなかった答え、承認待ちに合わない答え（もう閉じている、無い選択肢）は知らせない。
- 答えの無いまま期限で閉じた承認待ちは、本人の答えではないので知らせない。
- 許した答えの知らせには、承認待ちの id、承認待ちにした要求か先に頼んだことか、向け直し元、答えた時刻、操作と対象（生の操作は宛先・method・path）、選んだ選択肢と範囲（`once`・`timed`）と期限、出した許しの id を書く。先に頼んだことの承認待ちは、頼んだ操作をすべて並べる。
- 期限は、1 回の許しでは「この時刻までに使われなければ消える」時刻、期限付きの許しでは終わる時刻、期限の無い許しではそうと書く。
- 断った答えの知らせには、承認待ちの id と操作と対象を書く。
- 取り消しの知らせには、許しの id、もとの承認待ちの id、範囲、許しを出した時刻と期限、操作と対象を書く。

## 届け先

### Alertmanager に送る

- `-alertmanager-url` に Alertmanager の基の URL（`https://名前[:ポート][/path]`）を与えると、関所は知らせを、その下の `/api/v2/alerts` へ、Alertmanager の v2 の API の alert として POST する。Alertmanager から先（Slack の専用のチャンネルへの route）は、環境のリポジトリが持つ。
- 送るのは、作業環境の要求と同じ authd への送り口である。関所は上流へ直に出ない（ADR-0002）。authd の登録に Alertmanager の名前が無ければ、authd が断り、知らせは送れない。
- 送るたびに、関所自身の要求として記録に残す（`kind` が `gate`）。記録が書けなければ送らない。
- URL には、ユーザー・query・fragment を書けない。`https` でなければ使わない。

### 認証の要る入口

Alertmanager が、Bearer の token を確かめる入口（proxy など）の後ろにしか無いときは、`-alertmanager-surrogate` にサロゲートを与える。

- 関所は、知らせの要求のすべてに `Authorization: Bearer <サロゲート>` を付ける。authd は、登録したとおりに、それを本物の鍵に差し替えて Alertmanager へ送る（ADR-0003）。関所は本物の鍵を持たず、読まない。
- 付ける置き場所は `bearer`（scheme は `Bearer`）だけである。
- サロゲートは秘密ではないので、フラグに平文で与えてよい（ADR-0003）。ただし、記録・ログ・指標・知らせの本文には出さない。出す理由が無いためである。
- サロゲートに使えるのは、空白を含まない表示できる ASCII 文字だけである。それに合わなければ、URL が使えないときと同じに、知らせはログに出すだけになる。
- 与えなければ、知らせの要求に `Authorization` は付かない。
- `-alertmanager-url` 無しで与えても使わない。使わないことを標準エラーに出し、関所はそのまま動く（下の「Alertmanager を使わないとき」）。

関所が自分で上流へ出す要求には、もう 1 つ、GitHub のコネクタの問い合わせ（ADR-0003「関所自身の問い合わせも authd を通す」、ADR-0005）がある。2 つはサロゲートの出どころが違う。

| 要求 | 付けるサロゲート |
|---|---|
| コネクタの問い合わせ | 問い合わせのもとになった、作業環境の要求に付いていたサロゲート。要求を出した身元の権限を超えない |
| 知らせ | `-alertmanager-surrogate` で環境が関所に与えたサロゲート。知らせは作業環境の要求から生まれるのではなく、関所が自分で出すためである |

### alert の形

| 部分 | 中身 |
|---|---|
| label `alertname` | `SentinelFirstSeen`（初めて見る組）、`SentinelAnswer`（本人の答え）、`SentinelDailySummary`（まとめ） |
| label `severity` | いつも `info` |
| label `pair`・`key`・`source` | 初めて見る組の、組・中身・向け直し元の待ち受けの名前 |
| label `answer`・`approval`・`grant`・`source` | 本人の答えの、`allowed`・`denied`・`revoked` のどれか、承認待ちの id、取り消した許しの id（取り消しだけ）、承認待ちか許しの向け直し元 |
| label `day` | まとめの期間の始まりの日（`YYYY-MM-DD`、`-summary-timezone` で） |
| ほかの label | `-alert-label` に `名前=値` で与えたもの（繰り返せる）。どのインスタンスの関所かを示すのに使う |
| annotation `summary` | 1 行の要約 |
| annotation `description` | 詳しい文。まとめは複数の行になる |
| `startsAt` | 知らせることが起きた時刻（組を初めて見た記録の時刻、答えた・取り消した時刻、まとめの期間の終わり） |
| `endsAt` | 送った時刻の 1 時間後 |

- 知らせには解消という状態が無い。`endsAt` は送った時刻から決めるので、遅れて送った知らせも、1 度は届く。
- 初めて見る組の label の値と `summary` は 256 バイト、`description` は 2048 バイト、まとめの 1 行は 256 バイトで切り、切ったことを `…` で示す。path は作業環境が決めるもので、長くなりうるためである。

### 送れなかったとき

- 送れなかった知らせは関所のメモリの中で待ち、1 分ごとと、次の知らせができたときに送り直す。1 度に 100 件までをまとめて送る。
- 待てるのは `-notice-queue`（既定 1000）件までで、超えたら古いものから捨て、`sentinel_notices_dropped_total` に数える。
- 止まるときに、待っているものを 5 秒だけもう 1 度送ってみる。それでも送れなかったもの、関所が止まったときに待っていたものは失われる。初めて見た組は覚えに残るので、その日のまとめの「新しく現れた組」には出る。
- 送り損ないは指標に出る（[指標](metrics.md)）。

### Alertmanager を使わないとき

- `-alertmanager-url` を与えなければ、知らせは関所の標準エラーのログに出すだけにする。関所はそのまま動く。
- 知らせの設定（`-alertmanager-url`・`-alertmanager-surrogate`・`-alert-label`・`-summary-at`・`-summary-timezone`）が使えないときも、関所は起動する。使えないことを標準エラーに出し、URL かサロゲートが使えなければログに出すだけに、時刻や時間帯が使えなければ既定の値に倒す。知らせの設定は関所を止める理由にしない。`sentinel_notice_sender_configured` が 0 なら、知らせは Alertmanager へ届いていない。
- どちらの場合も、すべての知らせは送るかどうかによらず標準エラーに 1 行ずつ出る。

## 知らせに入れないもの

- 鍵・token・サロゲートの値、要求のヘッダ、要求と応答の本文、query は入れない。入るのは、何をしたか（操作と対象、または method と path）、どこへ（名前・IP とポート）、何件か、どう決めたか（理由）、本人の答えの範囲と期限までである。
- 本人の答えの知らせには、承認待ちの要約（`summary`）も許しの要約も入れない。要約には要求の query と本文の大きさが入るためである。操作の名前のある要求は、path も入れない（対象で示す）。
- path と、断った名前解決の名前は、作業環境が決めた値である。そこに書かれたものは、そのまま知らせに出る。

## 環境の側で要るもの

関所のリポジトリの外で、次のものを用意する。

| もの | 中身 |
|---|---|
| Alertmanager の HTTPS の名前 | authd は HTTPS でしか送らず、上流の証明書をその名前で確かめる。クラスタの中の Alertmanager を、TLS を終端する名前（Service の前の TLS の終端、Ingress など）で届くようにする |
| authd の登録 | `upstreams` に、その名前とポートを足す。証明書が自前の CA のものなら `ca_file` を書く |
| 鍵 | Alertmanager の入口に認証が無ければ、鍵の登録は要らない。Bearer の token を確かめる入口の後ろなら、authd の `credentials` に 1 件足す。`surrogate` に関所へ与えるサロゲート、`key_file` に入口が受け付ける token のファイル、`upstreams` に Alertmanager の上流の名前、`places` に `bearer` を書く（[authd の登録の形式](authd-registration.md)） |
| Alertmanager の route | `alertname` が `SentinelFirstSeen`・`SentinelAnswer`・`SentinelDailySummary` のものを、Slack の専用のチャンネルへ流す。1 件ずつ届くよう `group_by` に `pair` と `key`（答えは `answer`・`approval`・`grant`、まとめは `day`）を入れ、解消の知らせ（`send_resolved`）は切る |
| 関所のフラグ | `-alertmanager-url`、認証の要る入口なら `-alertmanager-surrogate`、インスタンスを示す `-alert-label`、本人の時間帯の `-summary-at` と `-summary-timezone` |
| 指標の scrape と規則 | 関所と authd の `-metrics-listen` を scrape し、[指標](metrics.md) の「知らせの規則に使うもの」の規則を置く |

関所自身の要求は、振り分け（[振り分けの形式](routes.md)）で決めない。Alertmanager の名前を振り分けに書く必要は無い。
