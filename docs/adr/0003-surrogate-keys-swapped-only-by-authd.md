# 0003. 道具にはいつもサロゲートを持たせ、authd だけが本物に差し替えて送る

- Date: 2026-11-09
- Updated: 2026-11-12（本人が許した表に無い宛先へは、登録の外の名前として鍵を付けずに送ることを足した。ADR-0007）
- Status: Accepted

## Context

運用の係（クラスタの運用を受け持つ natsumi のインスタンス）の道具は、鍵の要る API に話す。Kubernetes の API の ServiceAccount の token、GitHub の machine account の token、gated（クラスタの入口）の後ろの API の token などである。

今は、作業環境は鍵を 1 つも持たない。loopback の中継が、作業環境から来た `Authorization` と `Cookie` を捨てて、自分の鍵を付ける（natsumi の ADR 0085）。
この形は宛先ごとに loopback のポートがあることを前提にしている。ADR-0002 で道具が本物の URL に話す形にすると、中継のように「このポートに来たものにはこの鍵」とは決められない。
また、道具の多く（kubectl・`gh`・git）は、鍵が設定に無いと要求を送らないか、送り方を変える。

ここで使う言葉は次のとおりである。

- **本物の鍵**: 上流が受け付ける token やパスワード。
- **サロゲート**: 本物の鍵の代わりに道具に持たせる値。上流では使えず、authd の中で本物の鍵と対応付く。
- **置き場所**: 要求の中で鍵が入る場所。`Authorization` の Bearer、Basic のパスワード、決めたヘッダ、決めた query の引数。

## Decision

### 道具には、いつもサロゲートを持たせる

- 鍵の要る宛先には、道具にサロゲートを持たせる。道具はそれをふつうの鍵として扱う（kubeconfig の token、`GH_TOKEN`、git の Basic のパスワードなど）。
- サロゲートは秘密ではない。上流で使えず、authd の外では意味を持たないので、平文の設定（ConfigMap）に置いてよい。

### authd は鍵を持ち、上流へ送る係である

- 関所は、判定を済ませた要求を、サロゲートを付けたまま authd に渡す（ADR-0001 の Decision「部品の間は Unix socket でつなぎ、相手はカーネルに確かめさせる」）。関所は本物の鍵を見ない。
- authd は、開く宛先（ADR-0002 の Decision「扱いは宛先ごとに 3 つ」）の上流へのすべての通信を送る。鍵の要らない宛先も同じく authd が送る。名前解決、上流の証明書の確かめ、寿命の短い token の作り直しも authd が持つ。
- authd は、サロゲートごとに、登録した置き場所と、使ってよい上流の名前を持つ。
  - 登録した置き場所だけを探し、そこにある登録したサロゲートだけを本物の鍵に差し替える。
  - 本文は探さない。差し替えはヘッダと query だけで、要求の本文には手を付けない。
- authd は、関所が判定に使った宛先の名前でつなぎ、上流の証明書を確かめる。宛先ごとに CA を登録したもの（Kubernetes の API など）は、その CA で確かめる。
- authd はリダイレクトをたどらない。別の名前へ飛ぶ応答は、そのまま関所を通って作業環境に返る。作業環境がその先へ話せば、また関所の判定に掛かる。
- サロゲートの無い要求は、鍵を付けずにそのまま送る（鍵の要らない宛先。言語のパッケージの置き場など）。
- authd の UID の外向きは、上流のポートとクラスタの DNS に開く。iptables は名前で絞れず、上流の IP は変わりうるので、どの名前へ送るかは authd が登録で確かめる。

### authd も自分で確かめ、断ったことは関所が記録する

- authd は、関所の判定を信じるだけにしない。サロゲートと上流の名前の組が登録と合わなければ、差し替えずに要求を断る。
  - 例: Kubernetes の API のサロゲートを、GitHub への要求に載せた。
- 登録していない名前の宛先への要求は、サロゲートの有無にかかわらず断る。
  - 例外は、関所が本人の宛先の許しによる要求だと伝えたものである（2026-11-12、ADR-0007 の Decision「authd は、宛先の許しへの要求を、鍵を付けずに公のアドレスへ送る」）。authd はそれを、鍵を付けず、引いたアドレスが公のアドレスのときだけ、ポート 443 に送る。サロゲートが載っていれば差し替えずに断る。
- authd は断った理由を関所に返し、関所がそれを記録する（ADR-0006 の Decision「何を残すか」）。記録の正本は関所にあり、authd は記録を書かない。
- この確かめで防げるのは、関所の判定の誤りで鍵が別の宛先へ運ばれることである。乗っ取られた authd は登録した上流へ本物の鍵で何でも送れ、その分は関所の記録に残らない。authd を小さく保ち、関所と別の image にするのはこのためである。

### 関所自身の問い合わせも authd を通す

- 操作に揃えるために関所が上流に事実を問い合わせるとき（GitHub の node ID の引き直しや force push の見分け。ADR-0005）は、要求を出した身元のサロゲートで、authd を通して送る。
- 関所は鍵を持たず、問い合わせも要求を出した身元の権限を超えない。問い合わせは関所の問い合わせとして記録する（ADR-0006 の Decision「何を残すか」）。

### 鍵の正本

- 長く使う鍵（machine account の token など）は、環境のリポジトリで sops で暗号化した Secret を正本にし、authd にだけ mount する。
- 寿命の短い token（ServiceAccount の TokenRequest で作るものなど）は、authd が作り直す。作り直しに要る権限も authd にだけ渡す。
- 本物の鍵は記録（ADR-0006 の Decision「何を残すか」）にも、エラーの文にも出さない。

### サロゲートにできないもの

- mTLS のクライアント証明書と ssh の鍵は、置き場所で差し替える形にできない。最初の版では扱わない。
  - ssh の秘密鍵は、今の ssh-agent のコンテナのままにする（ADR-0002 の Decision「ssh」）。
  - mTLS が要る宛先が出たら、別の ADR で決める。

### 守る対象と、倒す向き

- 守るのは、本物の鍵の値が作業環境と関所に渡らないことと、本物の鍵が登録した上流にしか送られないことである。
- 許す範囲は、登録したサロゲート・置き場所・上流の名前の組だけである。宛先の許しによる要求は、鍵の無い要求としてだけ送る（2026-11-12、ADR-0007）。
- 合わないとき（組が登録と違う、登録の無い名前、鍵の正本が読めない、token の作り直しに失敗した）は、送らない側に倒す。サロゲートのまま上流に送ることもしない。

### 本 ADR で決定しないこと

- サロゲートの値の形と、登録（サロゲート・置き場所・上流の名前・CA の組）の形式（委譲先: authd の設定の仕様書）。
- 関所と authd の間で要求と断りを渡す形（委譲先: 関所と authd の実装の PR）。
- どの宛先にどの鍵を登録するか（委譲先: 環境のリポジトリの運用の係の配置）。
- 本人が画面から入れる鍵の置き方（委譲先: 汎用のコネクタを入れるときの ADR。2 番目の版の候補）。
- server の外の係への token を authd に移すこと（委譲先: 外の係への依頼を関所に通す、判定器を入れる版の ADR）。
- mTLS が要る宛先の扱い（委譲先: そういう宛先が要るようになったときの ADR）。

## Consequences

- 道具はふつうの設定で動き、設定を作業環境に置いてよい。鍵が無いと動かない道具も、サロゲートを本物と思って要求を送る。
- 作業環境から読めるのはサロゲートだけで、漏れても上流では使えない。
- 判定の誤りで鍵が別の宛先へ運ばれることは、authd の組の確かめで止まる。
- 本文は探さないので、サロゲートを本文に書いても本物にはならない。本文に鍵を入れる API は、そのままでは使えない。
- authd は上流へのすべての通信を受け持つので、鍵の保管庫より大きなプログラムになる。authd の UID は上流のポートに広く出られ、宛先を絞るのは authd の中の確かめになる。
- 乗っ取られた authd は、登録した上流へ本物の鍵で何でも送れる。それは関所の記録に残らない。
- ssh と mTLS は関所の外のまま残る。ssh の通信の中身は記録できない。
- authd が止まると、上流への通信が全部止まる（ADR-0001 の Decision「止まったら閉じる（fail closed）」）。

## Alternatives Considered

- **道具に鍵を持たせず、関所が宛先ごとに鍵を足す（今の中継と同じ）**: 鍵が無いと要求を送らない道具が多く、道具ごとにダミーの値を作る工夫が要る。ダミーの値に意味を持たせたのがサロゲートである。
- **関所に本物の鍵を持たせて差し替える**: 作業環境から来た入力を解くプロセスに鍵の値が載る（ADR-0001 の Alternatives Considered「関所に鍵も持たせる」）。
- **要求の全体（本文を含む）でサロゲートを探して差し替える**: 本文に書いたサロゲートが本物になれば、作業環境は本物の鍵を本文に載せて、上流の公開される場所（issue の本文など）へ書ける。
- **リダイレクトをたどる**: 許した宛先の応答が、登録していない宛先へ本物の鍵を運ぶ道になる。
- **authd の外向きを iptables で上流の IP に絞る**: 上流の IP は変わり、ほかの名前と IP を共有しうる。規則は初期化のコンテナが 1 度張るだけなので、IP が変われば黙って届かなくなる。
