# 0008. 表に無い宛先は、断った名前を関所が覚え、本人が許せば台帳の許しで通す

- Date: 2026-11-12
- Updated: 2026-11-13（宛先の許しの通信を、authd ではなく関所が直に送る形に書き直した。ADR-0007。私用の範囲のアドレスには、環境が渡す内側のドメインの一覧の名前だけをつなぐことにし、記録につないだアドレスを足した）
- Status: Accepted

## Context

関所（ADR-0001）は、作業環境から出ていく通信を、宛先ごとの扱い（振り分け）と操作ごとの allow・ask・deny（表）で決める（ADR-0002・ADR-0004）。この 2 つの層で、「決めていないもの」の扱いが違う。

- **表に無い操作**は、宛先の既定が ask なら、断らずに本人に聞く。本人が許せば、その場で通り、範囲付きの許しが台帳に残る（ADR-0004 の Decision「決めていないものは本人に聞く」）。
- **表に無い宛先**は、聞く道が無い。名前解決は振り分けにある名前にだけ答え、それ以外には NXDOMAIN を返す（ADR-0002 の Decision「名前解決は関所が受け、振り分けにある名前だけに答える」）。作業環境の道具からは、名前の無い宛先に見える。通すには、環境のリポジトリの振り分けに 1 行足す PR・CI・マージが要る。

運用の係（クラスタの運用を受け持つ natsumi のインスタンス）が、調べもののために初めての文書のサイトを読む、初めてのパッケージの置き場から取るといったことは、運用の中で日常に起きる。その都度、本人が環境のリポジトリを直すことになる。本人は「関所は、決めていないアクセスを基本的に承認待ちにする」ものだと理解していたが、宛先については実際はそうなっていない。

一方で、作業環境の道具は、利用者が頼んでいない名前も引く（テレメトリの送り先、更新の確かめなど）。断った名前のたびに承認待ちを作れば、承認待ちとその知らせ（natsumi の ADR 0096 の Web Push）は、本人が頼んでいない名前で埋まる。

今の関所には、次のことも関わる。

- 振り分けに無い名前は、上流の DNS に問い合わせずに NXDOMAIN を返す。問い合わせの名前そのものが外への持ち出しの道になるためである。断った名前は記録に残り、初めて見た名前は 1 件ずつ知らせる（ADR-0006 の Decision「いつもと違うことを知らせる」）。
- 開く宛先の TLS は関所の CA で終端する。平文の HTTP は開かず、すべて断っている。authd は HTTPS でしか上流へ送らない。
- authd は、起動のときに読む登録にある名前とポートにだけ送り、それ以外はサロゲートの有無にかかわらず断る（ADR-0003 の Decision「authd も自分で確かめ、断ったことは関所が記録する」）。登録は、変えたら authd の起動し直しが要る。
- 上流へ送るのは、最初の版から、宛先の許しの通信に限って関所になる（ADR-0007 の Decision「移す順番」）。この ADR はその形で書く。
- passthrough は元の宛先の IP の範囲とポートで決める（ADR-0002 の Decision「名前で決め、名前を引き直してつなぐ」）。関所の UID の外向きは、振り分けの passthrough の範囲にだけ開いている。
- 道具の中には、関所の CA では確かめず、自分の持つ CA でしか相手を確かめないものがある。運用の係が自分で作った試験用のクラスタの API server がその例で、開くと道具が動かない。
- 判定器（分類器）は、最初の版には無い（ADR-0001 の Decision「Muse と違えるところ」）。次の版で、聞かずに通す判断を判定器に足す見込みがある。

ここで使う言葉は次のとおりである。ADR-0002・ADR-0004 の言葉はそのまま使う。

- **表に無い宛先**: 振り分けに名前が無い宛先。振り分けで `deny` の名前と、振り分けに名前はあるがポートが違うものは含まない。
- **断った名前**: 表に無い宛先の名前のうち、作業環境が名前解決で引き、関所が NXDOMAIN を返したもの。
- **宛先の許し**: 本人が表に無い宛先に出す許し。操作の許し（ADR-0004 の「許し」）と同じく台帳に残る。
- **内側の名前**: 環境が渡す内側のドメインの一覧（Decision「内側のドメインの一覧は、環境が設定で渡す」）のドメインと、その下の名前。それ以外の名前を**外の名前**と呼ぶ。
- **私用の範囲**: インターネットで経路の無い、LAN と環境のクラスタの中（Service・Pod）のアドレス。ループバックとリンクローカルは含めず、別に扱う。

## Decision

### 表に無い宛先も、本人が許せば通る

- 表に無い宛先を、本人が許したら通す。許しは台帳に宛先の許しとして持つ。振り分けは書き換えない。
- 宛先の許しは、振り分けにある宛先と同じに、名前で決め、名前を引き直してつなぐ（ADR-0002 の Decision「名前で決め、名前を引き直してつなぐ」）。
- 振り分けが勝つ。振り分けに名前のある宛先（`deny` の名前と、ほかのポートで書かれた名前を含む）は、宛先の許しでは通さない。振り分けで断っている名前を、承認の画面から通す道は作らない（ADR-0004 の Decision「決めていないものは本人に聞く」の「deny も表のデータである」と同じ考え）。
- IP を直に書いた宛先は、今までどおり通さない。宛先の許しは名前にしか出せない。
- クラスタの中の名前（作業環境の名前解決の search の接尾辞の下の名前）にも、宛先の許しを出せる（本人の判断、2026-11-13）。振り分けにある名前に search の接尾辞を付けただけの名前には出せない。それは振り分けの名前を引く途中で道具が引く名前で、許す先ではない。
- 宛先の許しが効くのは、許しを出した向け直し元だけである（操作の許しと同じ）。

### 断った名前は覚えて一覧に溜め、本人が一覧から許す。知らせは出さない

- 関所は、断った名前を、向け直し元ごとに台帳に覚える。覚えには、いつ最初と最後に引かれたかと、何度引かれたかを残す。
- 本人は、承認の画面で断った名前の一覧を見て、そこから宛先の許しを出せる。
- 断った名前は、承認待ちにしない。承認待ちの知らせ（Web Push）も出さない。道具が勝手に引く名前で、承認待ちと知らせが埋まらないようにするためである。
  - 初めて断った名前の知らせ（ADR-0006 の Decision「いつもと違うことを知らせる」の「断った名前解決の名前」）は今までどおり出す。これは本人の答えを待つものではなく、Slack の専用のチャンネルに届くいつもと違うことの知らせである。
- 覚えの数には上限を置く。作業環境が名前をいくらでも作れるので、上限を超えたら古いものから落とす。落としても、記録には残る。
- 振り分けにある名前に search の接尾辞を付けただけの名前（ADR-0006 と記録の仕様書が知らせから外しているもの）は、一覧に載せない。

### 運用の係が先に頼んだときだけ、承認待ちにして知らせる

- 運用の係は、今ある「先に承認を頼む」口（ADR-0004 の Decision「先に頼めるのは、具体的な操作と対象の一覧だけ」）で、宛先の名前の一覧を頼める。新しい道具（ツール）は足さない。
- 頼んだ宛先は、1 つの承認待ちになり、今の承認待ちと同じに知らされる（natsumi の ADR 0096 の Web Push）。
- 頼めるのは名前だけである。範囲（下の「許しの単位と期限」と「許した宛先の扱い」）は、運用の係が指定できない。本人が画面で選ぶ。
- 振り分けにある名前、IP、関所自身の名前は頼めない。

### 許されていない宛先は、NXDOMAIN のまま見せる

- 許されていない表に無い宛先には、今までどおり NXDOMAIN を返す。作り物の IP を答えて、関所の案内の応答（403）を見せることはしない（ADR-0002 の Alternatives Considered「作り物の IP を答え、接続の先で名前に戻す（Muse の形）」を覆さない）。
- 運用の係は、作業環境向けの口の「自分の状態」で、最近断られた名前を読める。名前が引けないとき、関所が断ったのか本当に無い名前なのかを、そこで見分ける。
- **許されるまで、表に無い名前を上流の DNS に問い合わせない。** 断った名前の一覧にも、関所が引いた答えは載せない。問い合わせそのものが、名前に載せた持ち出しの道になるためである。

### 許しの単位と期限

- 単位は「この名前だけ」と「このドメインの下すべて」の 2 つで、既定はこの名前だけである。
  - 誰でも名前を作れるドメインを、一度に開けないようにする。下の名前が多い宛先（CDN など）は、本人の判断でドメインの下すべてに広げる。
  - 広げられるのは、登録できるドメイン（公開の接尾辞のすぐ下）までである。公開の接尾辞（`com` や、誰でも名前を登録できる共有のドメイン）そのものの下すべては許せない。
  - 公開の接尾辞の一覧は、ICANN の部と私設の部の両方を使う。誰でも名前を作れる共有のドメインは、私設の部に載っているためである。
  - 一覧のどの規則にも当たらない名前（クラスタの中の名前、内側だけで引ける名前、接尾辞が一覧に無い名前）も、一覧の既定の規則（最後の 1 ラベルを接尾辞とみなす）で決まる登録できるドメインまで広げられる。関所は、それより狭い上限を別に設けない。広く開きうることを分かったうえで、承認のたびに本人が広さを選ぶ（本人の判断、2026-11-13）。既定の選びは、ここでも「この名前だけ」である。
  - 承認の画面には、ドメインの下すべてを選んだときに通る広さを、関所が組んだ文ではっきり示す。一覧の既定の規則で決めたドメインなら、そのことも示す。
  - ドメインの下すべての許しも、振り分けにある名前には効かない（振り分けが勝つ）。
- 期限は、期限付き（選択肢は関所の設定）と期限なしの 2 つで、操作の期限付きの許しと同じ選択肢を使う（ADR-0004 の Decision「許しの範囲は「1 回」と「期限付き」の 2 つ」）。
- 宛先には「1 回」を置かない。サイトを 1 度読むにも、名前解決と要求は何本も飛ぶ。操作の「1 回」（要求 1 つ）と意味を食い違わせないため、その場だけ通したいときは、いちばん短い期限で代える。
- 期限が来たか取り消したら、その後の名前解決と新しい接続・要求には効かない。

### 許した宛先の扱い: 既定は開いて見る。passthrough も選べる

- 許した宛先は、既定では開く宛先と同じに扱う。関所の CA で TLS を終端し、要求を読み、記録する（ADR-0002 の Decision「扱いは宛先ごとに 3 つ」）。
- 本人は許すときに「開かない（passthrough）」も選べる。関所の CA で確かめない道具の宛先（運用の係が作った試験用のクラスタの API server など）のための例外である。
  - passthrough の宛先の許しは、TLS の SNI の名前で決め、その名前を関所が引き直してつなぐ。元の宛先の IP にはつながない。SNI の無い接続は通さない。
  - 中身を見ないので、記録は宛先・ポート・量・時間までになる。記録には中身を見ていないことが分かる形で残す。
  - passthrough では要求の読みと書きを分けられないので、下の「読みだけ」は効かない。passthrough を選ぶことは、その名前への中身を見ない通信を許すことである。
  - passthrough を選んだら、読みだけは選べない。承認の画面には、関所が「読み書きとも通る。中身は見ない」と示す。記録にも、その許しが読み書きとも通し、中身を見ないものだと分かる形で残す。

### 読みだけか、読み書きか。既定は読みだけ

- 開いて見る宛先の許しでは、本人が「読みだけ」か「読み書き」かを選ぶ。既定は読みだけである。
- 読みだけの許しは、表の「開く宛先の既定が ask で、規則が無い」宛先と同じに決める。読みの要求は通し、書きの要求は生の操作として ask にする（ADR-0004 の Decision「決めていないものは本人に聞く」）。書きは承認待ちになり、本人が許せば今の操作の許しの範囲（1 回・期限付き）で通る。
  - 読みと書きの分け方は、記録が読みと数えるものと同じにする（method で決める）。
- 読み書きの許しは、規則の無い宛先の既定が allow と同じに決める。書きも聞かずに通し、記録して、初めて見る書きを知らせる。
- 読みだけは、判定器が無い版で、「本人の情報が出ていきうるときに聞く」ことの代わりである。
- 読みだけでも、URL の query や path に載せて外へ出すことは防げない。これは受け入れる。記録は query を残し（ADR-0006 の Decision「何を残すか」）、初めての宛先の知らせと 1 日のまとめで気づく。

### ポートは 443 だけ

- 宛先の許しが効くのは、ポート 443 だけである。TLS として開く（または passthrough にする）。ほかのポートは、今までどおり振り分けの変更で足す。
- 平文の HTTP（ポート 80）は、宛先の許しでは通さない。関所は平文の HTTP を開かず、上流へも HTTPS でしか送らない。宛先の許しのためだけに、平文の道を作らない。
- 振り分けの passthrough の範囲に開けているポート 80（運用の係が自分で作る VM や試験用のクラスタへのもの）は変えない。これは IP の範囲とポートで決める今の passthrough で、宛先の許しとは別である。

### 宛先の許しの通信は、関所が鍵を付けずに直に送る

- 宛先の許しで通った要求と接続は、開いて見るものも passthrough も、関所が上流へ直に送る（ADR-0007 の Decision「移す順番」）。authd には渡さない。authd に、登録の外の名前へ送る例外は足さない。
- 関所は、ADR-0007 の Decision「上流へ送る部品が守ること」のとおりに送る。宛先の許しの通信では、さらに次を守る。
  - 鍵を付けない。許した宛先は authd の登録に無いので、差し替えは起きない。要求のヘッダか query に登録したサロゲートが載っていれば、サロゲートのまま上流へ出さず、その要求を断る。断ったことは記録に残す。
  - 私用の範囲（LAN と、環境のクラスタの中の Service・Pod のアドレス）につなぐのは、内側のドメインの一覧（下の節）のドメインの下の名前だけである。それ以外の名前（外の名前）は、許しても公のアドレスにだけつなぐ。外の名前を引いたアドレスが私用の範囲なら、つながずに断り、引いたアドレスとともに記録に残す。
  - ループバックとリンクローカル（メタデータの口を含む）のアドレスには、どの名前でもつながない。これらは Pod の中か、そのノードに閉じた宛先で、表に無い宛先として許す先ではない。
  - ポートは 443 だけである。
- 一覧の名前が私用の範囲のどの宛先へ届いてよいかは、関所ではなく、環境の側のネットワークの規則（NetworkPolicy など）が受け持つ。関所は、一覧の名前のつなぐ先が私用の範囲のどこかでは断らない。
- 内側の名前が公のアドレスを指したときは、断らずにつなぐ。その記録には、内側の名前が公のアドレスへつないだと分かる印を付ける。知らせは足さない（本人の判断、2026-11-13）。外からも内からも引ける名前や、公の宛先と内側の宛先を持つドメインでも動き、内側の名前の DNS が取られて外を指したことには記録で気づける。
- そのために、関所の UID の外向きに 443 を開ける。ループバックとリンクローカルは落とす（ADR-0007 の Decision「外へ出る道」）。authd に TCP の中継は持たせない。
- 乗っ取られた関所は、鍵の付かない要求を、環境の側の規則が許す範囲のどこの 443 へでも送れるようになる。これは受け入れる（下の Consequences）。

### 内側のドメインの一覧は、環境が設定で渡す

- 環境の側が、内側のドメインの一覧を、関所の設定として渡す。関所のコードに内側のドメインを決め打ちしない。今ある `-dns-search-suffix`（作業環境の名前解決が付ける接尾辞）とは別の設定にする。一覧は運用の係が書けない所に置く（振り分けと同じく、環境のリポジトリの配置）。
- 一覧の役は 2 つである。
  - 内側の名前の印: 一覧のドメインの下の名前は、承認の画面と記録で、内側の名前と分かるように示す。
  - 私用の範囲のアドレスにつないでよい名前の範囲（上の節）。
- 一覧は「ドメインの下すべて」の上限を決めない。上限は、上の「許しの単位と期限」のとおり、公開の接尾辞の一覧（と、その既定の規則）で決まる。
- 経緯: 2026-11-13 に、本人はまず、どの名前でも私用の範囲につなぐと決め、内側の守りを環境の側のネットワークの規則に任せた。その後、特別に扱う内側のドメインは環境の側で別に管理したいとして、私用の範囲につなぐ名前を、この一覧のドメインの下に限った。

### 判定は 1 か所にまとめ、判定器を後から差し込める形にする

- 「この要求・この接続・この名前解決を通すか、聞くか、断るか」を決める場所を、関所の中の 1 か所にまとめる。名前解決、TLS の握手、開いた要求のどれも、そこに聞く。宛先の許しの照合を、名前解決と接続と要求で別々に書かない。
- 判定の順は次のとおりである。
  1. 振り分けと表の deny。
  2. 振り分けと表の allow と規則。
  3. 台帳の許し（操作の許しと宛先の許し）。
  4. 判定器（この版には無い）。
  5. 残ったものは、操作は ask、表に無い宛先は断って覚える。
- 判定器は、4 の場所に後から差し込む。判定器にできるのは、5 で聞くか断るはずだったものを、通すかどうか決めることだけで、1 の deny と 3 の許しは変えられない。判定器の入れ方と、何を判定器に見せるかは、判定器を入れる版で決める。

### 承認の画面の文は、関所が事実から組む

- 宛先の承認待ちと、断った名前の一覧に出す文は、関所が事実から組む。事実は、名前、向け直し元、断った回数と最初・最後の時刻、ドメインの下すべてに広げたときのドメインである。運用の係が書いた文（頼む理由など）は使わない（ADR-0004 の Decision「先に頼めるのは、具体的な操作と対象の一覧だけ」と同じ）。
- 名前は作業環境が決めた値である。画面は平文として出し、リンクとして解かない（natsumi の ADR 0096）。

### 記録と知らせ

- 宛先の許しで通った要求・接続・名前解決は、許しの id とともに記録に残す。何で通ったか（振り分けか、宛先の許しか）が記録で分かるようにする。
- 関所が上流へ直に送った要求と接続の記録には、関所が名前を引き直して実際につないだアドレスを残す。引いたアドレスで断ったとき（ループバック・リンクローカル、外の名前の私用の範囲）は、引いたアドレスを残す（ADR-0006 の改め）。
- 内側のドメインの一覧の名前への記録には、内側の名前だと分かる印を付ける。 内側の名前が公のアドレスへつないだ記録には、そのことの印も付ける。
- 本人が宛先の許しを出したこと（承認待ちへの答えでも、断った名前の一覧からでも）と取り消したことは、本人の答えとして記録に残し、1 件ずつ知らせる（ADR-0006 の Decision「いつもと違うことを知らせる」の「本人の答えを受けたことを、1 件ずつ知らせる」）。関所は server の答えを信じるので、偽った許しに気づけるようにする。
- 新しく許した宛先は、そこへ初めて通った要求で「初めて見る組」の宛先として知らせ、1 日のまとめの新しく現れた組にも出る。passthrough の宛先の許しは、名前とポートの組で知らせる。
- 許した宛先からのリダイレクトの先が、振り分けにも台帳にも無い名前なら、それは別の表に無い名前として断られ、一覧に載る（関所はリダイレクトをたどらない。ADR-0007）。

### 守る対象・許す範囲・失敗したときの倒し方

- 守るのは、本人が許していない表に無い宛先へ、作業環境の通信が出ないことと、表に無い宛先に鍵が届かないことと、許すかどうかを決める道がモデルに無いことである。
- 許す範囲は、振り分けの open と、台帳の宛先の許しの名前（またはドメインの下）・向け直し元・ポート・期限・扱いに当てはまるものだけである。
- 倒す向き:
  - 台帳を読めないときは、宛先の許しが無いものとして扱う。名前解決は NXDOMAIN、接続と要求は断る。
  - 断った名前を覚えられないときも、断ることは変わらない（覚えは本人の便宜で、守りではない）。そのことは記録と指標に出す。
  - 記録が書けなければ通さない（ADR-0006 の Decision「記録が書けなければ、通さない」）。
  - 関所は、引いたアドレスがループバックかリンクローカルのもの、外の名前で引いたアドレスが私用の範囲のもの、上流の証明書を確かめられないもの、サロゲートが載ったものを、宛先の許しがあっても送らない。
  - 内側のドメインの一覧が読めないときは、一覧が空のものとして扱う（どの名前も私用の範囲につながない）。

### 適用範囲

- 対象は、運用の係のインスタンスの作業環境の出口だけである（ADR-0001 の Decision「適用範囲」）。

### 本 ADR で決定しないこと

- 判定器（聞かずに通す判断）の入れ方と、判定器に見せるもの（委譲先: 判定器を入れる版の ADR）。
- 断った名前の覚えの上限の数と、覚えておく長さ、一覧の並べ方（委譲先: 関所の実装の PR と関所の仕様書 `docs/destination-grants.md`）。
- 台帳・承認の口・作業環境向けの口・記録・知らせ・指標の欄と形（委譲先: 関所の仕様書 `docs/destination-grants.md` と `docs/approvals-api.md`）。
- ループバックとリンクローカルと私用の範囲の決め方、内側のドメインの一覧の設定の形、関所が登録したサロゲートの値を知る形（委譲先: 関所の実装の PR）。
- 公開の接尾辞の一覧の持ち方と、新しくする方法（委譲先: 関所の実装の PR）。
- 承認の画面に断った名前の一覧と宛先の許しの選択肢を並べること（委譲先: natsumi の承認の画面の ADR と実装。natsumi の ADR 0096 を追うもの）。
- 環境の側の規則（宛先の許しのための関所の UID の 443、内側の宛先を守るネットワークの規則）と、内側のドメインの一覧の中身（委譲先: 環境のリポジトリの運用の係の配置）。

## Consequences

- 初めての宛先を、環境のリポジトリの PR とマージを待たずに、本人が承認の画面から通せる。運用の係が先に頼めば、その場で知らせが届く。
- 断った名前は一覧に溜まるだけで知らせが出ないので、本人は、運用の係が頼まない限り、一覧を見に行かないと気づかない。運用の係が名前を引けずに止まったときは、運用の係が状態を読み、先に頼む必要がある。
- 許されていない名前は NXDOMAIN のままなので、道具のエラーは「名前が無い」になる。運用の係が関所の断りと取り違えることがある。取り違えが多ければ、作り物の IP と関所の案内の応答を後で考える。
- 許された宛先も既定で開いて見るので、出ていく書きの本文は記録に残る。読みだけの既定で、書きは本人に聞かれる。
- 読みだけでも、query と path で持ち出せる穴は残る。防がずに、記録と知らせで気づく。
- passthrough の宛先の許しでは、中身は見えない。その宛先で何をしたかは、名前・量・時間しか残らない。
- https の無い宛先（平文の HTTP でしか話さないもの）には、今と同じく届かない。関所は、振り分けの宛先でも宛先の許しでも、平文の HTTP を開かない。
- 宛先の許しで、内側のドメインの一覧の名前なら、クラスタの中や LAN のサービスにも、振り分けを直さずに届く。内側のドメインを足すのは、環境の側の設定の変更である。
- 一覧に当たらない内側の名前では、ドメインの下すべての許し 1 つで、広い範囲（たとえばクラスタの中の名前のほぼ全部）が通りうる。広さを選ぶのは本人で、承認の画面の文がその広さをはっきり示すことに頼る。
- クラスタの中の Service や Pod へは、Kubernetes の API server を通らずに直に届く。API server の権限の確かめ（RBAC）と監査のログ（ADR-0001 の Decision「床は環境が守る。関所はそれが成り立つことを前提にする」）は通らない。そうした通信の手がかりは、関所の記録だけになる。
- 内側の守り（一覧の名前がどの内側の宛先へ届いてよいかのネットワークの規則）は、環境の側が用意する。それが入る前に一覧を渡して宛先の許しを使えるようにすると、内側の 443 への守りの無い期間ができる。
- 許した外の名前が、あとから内側のアドレスを指すように変えられても、関所は私用の範囲につながずに断る。断ったことは、引いたアドレスとともに記録に残る。
- 記録には、関所が名前を引き直して実際につないだアドレスが残る（下の「記録と知らせ」）。作業環境に答えたアドレス（`dnsAnswer`）や元の宛先（`address`）と食い違っても、どこへ届いたかが分かる。
- 関所の UID は、443 へ直に出られる（ループバックとリンクローカルを除く）。乗っ取られた関所は、鍵の付かない要求を、環境の側の規則が許す範囲のどこへでも送れる。今は、関所は passthrough の範囲と authd の登録の外へは出られない。持ち出しは防がないこと（ADR-0001 の Decision「関所が守るもの」）と、鍵付きの通信が authd を通り、鍵が登録した上流にしか届かないことは、最初の版では変わらない。
- authd は変わらない。宛先の許しの通信は authd を通らないので、authd が止まっていても届く。
- 振り分けが勝つので、振り分けにある名前のほかのポートや、振り分けで断った名前を、本人が画面から通すことはできない。そのときは振り分けを直す。
- 期限の無い宛先の許しは、取り消すまで効き続ける。棚卸しは本人の画面に頼る。
- 判定の場所を 1 つにするので、名前解決・接続・要求の判定の書き方が変わる。判定器を後から足すときは、その 1 か所に足せばよい。

## Alternatives Considered

- **断った名前ごとに承認待ちを作って知らせる**: 道具が頼まれずに引く名前（テレメトリ・更新の確かめ）で、承認待ちと知らせが埋まり、本当に要るものが見落とされる。
- **作り物の IP を答え、関所の案内の 403 で承認待ちの id を見せる**: 運用の係は断りを取り違えにくくなるが、名前と作り物の IP の対応を関所が持ち続けることになる（ADR-0002 で退けた理由と同じ）。まず NXDOMAIN と状態の口で始め、取り違えが多ければ考え直す。
- **許した宛先を振り分けに書き足す（関所が環境のリポジトリに PR を出す）**: 許すたびに PR・CI・マージが要り、今の困りごとが残る。期限付きの許しも表せない。
- **断った名前を、許す前に上流の DNS に引いて一覧に答えも見せる**: 問い合わせそのものが名前に載せた持ち出しの道になる。
- **宛先にも「1 回」を置く**: 1 度の閲覧で名前解決と要求が何本も飛ぶので、1 回が何を指すか決められない。操作の「1 回」と意味が食い違う。
- **許した宛先は既定で passthrough にする**: 中身が記録に残らず、書きを本人に聞けない。開いて見る今の扱いと揃えた。
- **つなぐ先を公のアドレスに限る（クラスタの中・LAN の私用の範囲にはつながない）**: 許した外の名前が内側を指すように変えられても、内側に届かない。しかし本人は、許した名前で内側のサービスにも届かせたい（本人の判断、2026-11-13）。
- **どの名前でも私用の範囲につなぎ、内側の守りを環境の側のネットワークの規則だけに任せる（2026-11-13 に一度決めた形）**: 許した外の名前があとから内側を指すように変えられると、規則が許す内側の 443 に届く。本人は、特別に扱う内側のドメインを環境の側で別に管理し、その名前だけを私用の範囲につなぐことにした。
- **一覧に当たらない名前は「この名前だけ」でしか許せないようにする**: 内側の名前で広く開くことは無くなるが、下の名前の多い内側のサービスは名前ごとに許すことになる。本人は、広さを承認のたびに自分で選ぶことにした。
- **内側の名前が公のアドレスを指しても、印を付けずにつなぐ**: 記録のつないだアドレスを読めば分かるが、内側の名前が外を指したことが記録の上で目立たない。
- **内側の名前は、私用の範囲のアドレスにだけつなぐ（公のアドレスなら断る）**: 内側の名前の DNS が取られて外を指しても止まるが、公の宛先を持つ内側のドメインや、外からも内からも引ける名前が使えない。
- **内側のドメインの一覧と `-dns-search-suffix` を 1 つの設定にまとめ、種類の印で分ける**: 設定は 1 つになるが、意味の違う 2 つ（名前解決の接尾辞と、つないでよい範囲）が同じ所に並び、種類を誤れば私用の範囲が開く。
- **`-dns-search-suffix` の接尾辞を、自動で内側のドメインに入れる**: 設定の手間は減るが、クラスタの中が本人の明示なしに私用の範囲につながる。本人は、特別に扱う内側のドメインを別に管理したい。
- **内側のドメインの一覧に、「下すべて」の上限も持たせる**: 内側の名前でも下すべてを適切な広さで選べるが、一覧の宣言を誤れば広く開き、一覧の役が増える。本人が承認のたびに広さを選ぶので、上限を一覧で持つ必要は無い。
- **ポートを本人が選べるようにする**: ほかのポートの多くは HTTP でなく、開いて見られない。443 に限れば開いて見る前提と合う。
- **443 と 80 を許す（80 は平文の HTTP として開き、平文で送る）**: 今の関所は平文の HTTP を開かず、authd も HTTPS でしか送らない。宛先の許しのためだけに平文の道を作ると、平文の扱いと「平文には鍵を差し替えない」決まりが増え、振り分けの宛先とで平文の扱いが食い違う。
- **80 は関所が https への転送の応答を返すだけにする**: 道具が転送をたどらない（`curl` の既定など）と使えず、https の無い宛先には届かない。80 を外すのと比べて得るものが少ない。
- **authd の登録に、許した宛先を書き足して起動し直す**: 許すたびに authd を起動し直すことになり、許しの期限と取り消しも authd の登録に写すことになる。
- **authd に、登録の外の名前へ鍵を付けずに送る例外を足す（2026-11-12 の案）**: 鍵の分離は保てるが、authd が台帳の許しを関所の言葉で受け取って送る道が増え、passthrough のためには関所の UID にも 443 が要るので、出口は 2 つに分かれたままになる。本人は出口を関所に寄せることを選んだ（ADR-0007）。
- **宛先の許しの判定を、名前解決・TLS・要求のそれぞれに足す**: 照合の書き方が 3 か所に分かれ、食い違えば名前は引けるのに接続が断られる、といったことが起きる。判定器を足す場所も 3 か所になる。
