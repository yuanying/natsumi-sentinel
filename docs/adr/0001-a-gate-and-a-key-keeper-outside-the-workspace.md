# 0001. 作業環境の外に関所と鍵の番を分けて置き、鍵の要る操作を判定と記録に通す

- Date: 2026-11-09
- Status: Accepted

## Context

natsumi は、本人専用の AI の秘書のサーバーである。インスタンスごとに 1 つの Pod で動き、Pod の中には少なくとも次のコンテナがある。

- **作業環境**（workspace）: モデルがシェルのコマンドや Codemode のスクリプトを動かす場所。外から読んだ文書をそのまま扱うので、乗っ取られうる場所として扱う。
- **server**: natsumi 本体。会話の思考ループ、外の係（A2A のエージェント）への依頼、本人向けの画面を持つ。
- **出口**（egress）: nginx の中継。作業環境の外向きの通信は、ここを通るものだけが出られる。

インスタンスの 1 つに、クラスタの運用を受け持つもの（以下「運用の係」）がある。運用の係は Kubernetes の API・GitHub・脆弱性の一覧などの API を使うので、今は出口の中継が API ごとに鍵を付けている（natsumi の ADR 0085）。
この形で、次のことが起きている。

- **中継の判定は「通す」か「403」の 2 つしかない。** 本人に聞く、聞いた答えを覚える、という道が無い。GitHub の書き込みは中継のスクリプトの許可リストで決めていて、1 つ許すたびに環境のリポジトリの PR・テスト・apply・Pod の作り直しが要る。
- **本人の「ok」を中継が確かめられない。** 運用の係のマージの ok は会話の中で取っている。乗っ取られた運用の係は ok を偽れ、中継が見られるのは許可リストと head の SHA だけである。
- **何が出ていったかの記録が薄い。** 中継のアクセスログは method・パス・状態・時間だけで、出ていった書き込みの本文は残らない。

natsumi は、インスタンスをできるだけ自由に動かし、守りは「防ぐ」より「すぐ気づく」に寄せる方針を取った（natsumi の ADR 0095）。
防ぐことで守る範囲（床）は、監視そのものを壊せないことと、本人の私事と本人に代わる約束に絞り、床の外の行為は許したうえで記録し、異常の知らせで気づく。防ぐことを緩めるときは、気づく手段を同じ時に用意する。
この ADR は方針を決め直さず、その方針のもとで関所が何を受け持つかを決める。

Meta は、エージェントの Muse の守りを公開している。エージェントの本体を閉じ込めた領域（runtime cell）の外に、出口と操作の許可を出す唯一の権限である Sentinel と、資格情報を保管する hatch-authd を置く。
エージェントには代理の token（サロゲート）だけを見せ、Sentinel が許した後に出口で本物と差し替える。cell と各サービスは Unix socket でつながり、相手はカーネルが `SO_PEERCRED` で確かめる。承認は会話の外でクライアントの画面から取り、範囲の決まった権限として扱う。

## Decision

### 関所と authd を、natsumi とは別のプログラムとして作る

- 作業環境から外への通信の判定と記録を受け持つ **関所**（sentinel）と、鍵を持って上流へ送る **authd** を作る。Muse の Sentinel と hatch-authd に当たる。
- authd は鍵の保管庫ではなく、関所が判定した要求をすべて上流へ送る送信係である。名前解決、上流の証明書の確かめ、寿命の短い token の作り直しも authd が持つ（ADR-0003）。
- 2 つは別のプログラム、別の image にする。分けて守れるのは、**鍵の値が、作業環境から来た敵意のある入力を解く関所のプロセスに無い**ことである。乗っ取られた関所も、乗っ取られた authd も、登録した宛先へは鍵の力をそのまま使えるので、分けても宛先ごとの鍵の使い道は守れない。それは判定と記録（ADR-0004・ADR-0006）と、外の床（下の節）が受け持つ。
- 2 つとも natsumi のリポジトリではなく、このリポジトリに置く。natsumi の image は全インスタンスで共通で、関所を使わないインスタンスに関所のコードを持ち込まない。
- natsumi の側に残すのは、本人が承認する画面とその窓口である。これは natsumi の ADR が決める。

### 置き場所は、守るインスタンスの Pod の中の別のコンテナ・別の UID

- 関所と authd は、守るインスタンスの Pod の中に、それぞれ別のコンテナとして置く。UID も作業環境・server・互いと別にする。
- 同じ Pod に置くのは、作業環境の通信を同じ network namespace の中で関所へ向け直す（ADR-0002 の Decision「作業環境の通信は、iptables で関所に向け直す（透過プロキシ）」）ためである。
- 作業環境の UID は、向け直しの先と、関所の作業環境向けの口にしか届かない。authd と、承認を受け付ける口には届かない。

### 部品の間は Unix socket でつなぎ、相手はカーネルに確かめさせる

- 関所と authd の間、server と関所の間は、それぞれの 2 つのコンテナだけが mount する Unix socket でつなぐ。
- 受ける側は、接続の相手の UID を `SO_PEERCRED` で確かめ、決めた UID 以外を断る。authd は関所の UID だけ、承認を受け付ける口は server の UID だけを受ける。
- 部品の間に共有の秘密（パスワードや token）を置かない。盗まれる秘密が無ければ、作業環境から部品になりすます道も無い。

### 承認を決められるのは本人だけで、会話の外で取る

- 関所は、本人の答え（許す・断る・範囲）を、server の UID からの socket でだけ受け付ける。server は本人の認証の後ろの画面から、その答えを渡す。
- 作業環境と、モデルが呼べるツールには、承認を決める道を渡さない。モデルにできるのは、承認を頼むことと、自分の承認待ちや許しを読むことだけである（ADR-0004 の Decision「運用の係は、自分の状態を読むだけ」）。
- 会話の中の「ok」は、承認として数えない。
- 関所は server の答えを信じる。したがって、承認を本人だけが決められるのは、server が健全なあいだに限られる。そのため関所は、受けた答えをすべて自分の記録に残し、1 件ずつ知らせる（ADR-0006 の Decision「いつもと違うことを知らせる」）。server が偽った承認にも、後から気づけるようにする。

### 関所が守るもの

- 守るのは、**鍵の要る操作が、関所の判定と記録を通らずには行えない**ことである。本物の鍵は authd にしか無く、authd へは関所からしか届かない。
- 関所は持ち出しを防がない。運用の係が作る VM からの外向きと、運用の係の private のリポジトリで動く GitHub Actions は、関所を通らない出口として残る（下の「本 ADR で決定しないこと」）。
- 関所の役目は、出ていくものをすべて記録し（ADR-0006 の Decision「何を残すか」）、決めていない操作を本人に聞き（ADR-0004 の Decision「決めていないものは本人に聞く」）、範囲付きの許しで聞く回数を減らすことと、いつもと違うことを知らせることである。
- 断る操作も、関所のコードには固定しない。表のデータとして持ち、環境のリポジトリの変更で変えられる（ADR-0004 の Decision「宛先ごとの既定と規則で、allow・ask・deny を決める」）。

### 床は環境が守る。関所はそれが成り立つことを前提にする

natsumi の ADR 0095 の床のうち「監視そのものを壊せない」ことは、関所ではなく環境（クラスタの権限の仕組み）が守る。関所の守りは、次の条件が環境で成り立っていることを前提にする。

- 運用の係の ServiceAccount は、次のものに書けない（ValidatingAdmissionPolicy で拒む）。
  - 運用の係の Pod・関所・authd・その記録の置き場のある名前空間。
  - 監視の部品（Prometheus・Alertmanager・ログの溜め場）のある名前空間。
  - control plane の名前空間と、強い権限の ServiceAccount のある名前空間。
  - RBAC・ValidatingAdmissionPolicy・Webhook。
- 運用の係が作る・直す Pod は、別の身元に乗り換えられない。default 以外の ServiceAccount、hostPath、特権、host の名前空間を使えない（Pod Security の baseline と、ServiceAccount の縛り）。
- 運用の係が GitOps の仕組み（Argo CD）に頼めるのは同期だけで、同期する中身は変えられない。
- 関所と authd の死活の知らせ（dead man's switch）の受け手は、クラスタの外に置く。クラスタごと取られても、途絶えたことが外から本人に届く。

さらに、natsumi の ADR 0095 の「気づく手段の無いまま緩めない」を、関所の側の守る条件として次のように置く。

- **運用の係の ServiceAccount の RBAC を、読みより広げるのは、クラスタの API server の監査のログと、クラスタの外の dead man's switch が動いてからにする。** 関所はクラスタの中で起きたこと（運用の係が作った workload のふるまい）を見られないので、Kubernetes の書きに気づく手段は API server の監査のログになる。

### 止まったら閉じる（fail closed）

- 関所が止まっていれば、作業環境の外向きは出られない。関所を迂回する道は作らない。
- authd が止まっていれば、鍵の要る通信も鍵の要らない通信も上流へ出られない（関所は上流へ直に出ないため。例外は ADR-0002 の Decision「扱いは宛先ごとに 3 つ」の passthrough）。
- 設定（振り分け・表）が起動のときに読めなければ、関所は起動しない。監査の記録が書けなければ、その要求は通さない（ADR-0006 の Decision「記録が書けなければ、通さない」）。
- 失敗のときは、通さない側に倒す。

### 適用範囲

- 最初に入れるのは、運用の係のインスタンスの作業環境の出口だけである。
  - server の外向き（外の係への依頼、モデルの経路、Slack への送信）は関所に通さず、今の出口のままにする。外の係への依頼を関所に通すのは、判定器を入れる版で決める。
  - ほかのインスタンスは今の出口（natsumi の ADR 0034・0085）のままで、natsumi の関所に関わる機能は設定で off が既定である。
- 運用の係で形が固まったら、ほかのインスタンスへ広げる。広げるときに変わることがあれば、別の ADR で決める。

### Muse と違えるところ

- 閉じ込めは VM と `systemd-nspawn` ではなく、Kubernetes の Pod の中のコンテナと UID で作る。今の natsumi の閉じ込めがこの形で、1 インスタンスに 1 つの Pod である。
- プロセスごとの汚れの追跡（tainted egress）はしない。eBPF と LSM の仕組みはこの規模に見合わず、ここではインスタンスごとに分けることで代える。
- connector の処理を cell の外の worker で動かす形（privsep）は取らない。道具は作業環境の中で本物の URL に話し、関所が通信の側で要求を操作に揃える（ADR-0002・ADR-0005）。操作に揃えるのに上流の事実が要るとき（GitHub の node ID の引き直しなど）は、関所の中のコネクタが、要求を出した身元のまま authd を通して問い合わせる。
- 最初の版には判定器（分類器）を入れない。最初の版で確かめるのは、聞くことと範囲付きの許しで運用の係に任せられることが増えるかと、通したものの中のいつもと違うことに気づけるかである。

### 本 ADR で決定しないこと

- 判定器（出ていく文・入ってくる文の injection・操作の意味の判定）の入れ方と、server の外の係への依頼を関所に通すこと（委譲先: 判定器を入れる版の ADR。最初は点数の記録だけで入れ、数日見てから効かせる）。
- 汎用のコネクタ（本人が画面で宛先と鍵を登録し、デプロイせずに使う形。Muse のカスタムコネクタに当たる）（委譲先: 2 番目の版の候補として、入れるときの ADR）。
- natsumi の側の承認の画面と窓口（委譲先: natsumi の ADR 0096）。
- 床の条件の中身（ValidatingAdmissionPolicy・Pod Security・ServiceAccount の縛り・RBAC の範囲、dead man's switch の外の受け手）（委譲先: 環境のリポジトリの運用の係と監視の配置）。
- クラスタの API server の監査のログと、ログの溜め場、異常の規則（委譲先: クラスタの監査の作業単位。環境のリポジトリとクラスタの manifest のリポジトリ）。
- 運用の係が作る VM からの外向きの通信と、運用の係の private のリポジトリで動く GitHub Actions（委譲先: 本人が別に手当てする。手当てを決めたら別の ADR）。

## Consequences

- 本人に聞く道ができる。表に無い操作は断らずに聞くので、運用の係に任せられることが、許すたびに PR と apply をせずに増えていく。
- 本人の承認は会話の外で取り、関所が台帳で確かめる。運用の係が会話で ok を偽っても、操作は通らない。
- 鍵の値は authd の中にしか無く、関所も作業環境も本物の鍵を見ない。
- 鍵の要る操作はすべて関所の記録に残り、初めて見るものは知らされる。
- 部品が増える。Pod のコンテナが 2 つ増え、それぞれの image の版上げとリリースが要る。authd は上流へのすべての通信を受け持つので、見た目より大きなプログラムになる。
- 関所と authd が止まると、運用の係の作業環境は外に出られない。止まったことは、クラスタの外の dead man's switch で知る。
- 承認は server の健全さに依る。乗っ取られた server は自分で承認を出せ、記録の本文も読める。関所が答えを 1 件ずつ記録して知らせるので、後から気づけるが、出た後の操作は止められない。
- 持ち出しは防がない。VM と Actions の出口を手当てするまで、運用の係は関所を通らずに外へ出せる。関所が守るのは鍵の使い道までである。
- 「自由にさせて気づく」なので、床の外の操作（RBAC で許した範囲の Kubernetes の書きなど）は、事後に記録と知らせで気づく。気づく前に起きた変更は、元に戻す作業が要る。
- RBAC を広げるのは監査のログと外の dead man's switch が動いてからなので、それまでは Kubernetes の書きは今と同じく運用の係に任せられない。
- 判定器が無いので、出ていく文に私事が混ざっても、最初の版の関所は記録して知らせるだけで止めない。

## Alternatives Considered

- **今の nginx の中継に、聞く道と台帳を足す**: 中継の判定は nginx の設定とスクリプトで書かれ、状態を持たない。台帳・承認待ち・範囲付きの許しを持たせるには、別のプログラムが要る。
- **関所を natsumi の server の中に作る**: server は作業環境と同じ Pod にあり、モデルを動かす本体でもある。判定と記録を server に置くと、server が乗っ取られたときに判定も記録も一緒に失う。natsumi の image を全インスタンスで共通に保てなくなる。承認は server の健全さに依るが、記録と知らせは server の外に残る。
- **関所を Pod の外（クラスタの共有のプロキシ）に置く**: 作業環境の通信を Pod の外へ向け直すには、CNI や NetworkPolicy の層での向け直しが要る。同じ Pod の中なら、今の出口と同じ iptables の初期化で済む。
- **関所に鍵も持たせる**: 作業環境から来た入力を解くプロセスに鍵の値が載る。解く側の不具合が鍵の漏れに直結する。
- **部品の間を TCP と共有の token でつなぐ**: token が漏れれば作業環境から部品になりすませる。Unix socket と `SO_PEERCRED` なら盗まれる秘密が無い。
- **床を運用の係の ServiceAccount の名前で絞る 2 枚の ValidatingAdmissionPolicy だけにする**: 運用の係は、ほかの名前空間に Job を作って強い ServiceAccount を名指しするか、control plane の workload を直せば、別の身元で床の外に出られる。身元の乗り換えと control plane を塞がなければ、監視を壊せないとは言えない。
- **最初の版から外の係への依頼も関所に通す**: 判定器の無い版では記録が 1 か所に揃うだけで、server の側の変更と、関所が止まったときに係に頼めなくなることを払う。最初の版で確かめたいことに効かない。
