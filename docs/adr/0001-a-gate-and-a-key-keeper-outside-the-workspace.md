# 0001. 作業環境の外に関所と鍵の番を分けて置き、自由にさせて記録で気づく

- Date: 2026-11-09
- Status: Accepted

## Context

natsumi は、本人専用の AI の秘書のサーバーである。インスタンスごとに 1 つの Pod で動き、Pod の中には少なくとも次のコンテナがある。

- **作業環境**（workspace）: モデルがシェルのコマンドや Codemode のスクリプトを動かす場所。外から読んだ文書をそのまま扱うので、乗っ取られうる場所として扱う。
- **server**: natsumi 本体。会話の思考ループ、外の係（A2A のエージェント）への依頼、本人向けの画面を持つ。
- **出口**（egress）: nginx の中継。作業環境の外向きの通信は、ここを通るものだけが出られる。

インスタンスの 1 つに、クラスタの運用を受け持つもの（以下「運用の係」）がある。運用の係は Kubernetes の API・GitHub・脆弱性の一覧などの API を使うので、今は出口の中継が API ごとに鍵を付けている（natsumi の ADR 0085）。
この形で、次のことが起きている。

- **中継の判定は「通す」か「403」の 2 つしかない。** 本人に聞く、聞いた答えを覚える、という道が無い。GitHub の書き込みは中継のスクリプトの許可リストで決めていて、1 つ許すたびに環境のリポジトリの PR・テスト・apply・Pod の作り直しが要る。
- **本人の「ok」を中継が確かめられない。** 運用の係のマージの ok は会話の中で取っている。乗っ取られた運用の係は ok を偽れ、中継が見られるのは許可リストと head の SHA だけである。
- **何が出ていったかの記録が薄い。** 中継のアクセスログは method・パス・状態・時間だけで、出ていった書き込みの本文は残らない。

本人は、natsumi の狙いを「AI のエージェントにどれだけのことができるかを知る」に寄せることにした。守りは「防ぐ」より「自由にさせて、すぐ気づく」を主にする。
床（何があっても越えさせない線）は、監視そのものを壊せないことに絞り、その代わりに監査と異常の知らせを厚くする。
本人の私事（記憶・会話・メールなど）が外へ出ることと、本人に代わって約束をすることには、引き続き気をつける。

Meta は、エージェントの Muse の守りを公開している。エージェントの本体を閉じ込めた領域（runtime cell）の外に、出口と操作の許可を出す唯一の権限である Sentinel と、資格情報を保管する hatch-authd を置く。
エージェントには代理の token（サロゲート）だけを見せ、Sentinel が許した後に出口で本物と差し替える。cell と各サービスは Unix socket でつながり、相手はカーネルが `SO_PEERCRED` で確かめる。承認は会話の外でクライアントの画面から取り、範囲の決まった権限として扱う。

## Decision

### 関所と authd を、natsumi とは別のプログラムとして作る

- 作業環境から外への通信の判定と記録を受け持つ **関所**（sentinel）と、鍵を保管して本物の鍵を付けて上流へ送る **authd** を作る。Muse の Sentinel と hatch-authd に当たる。
- 2 つは別のプログラム、別の image にする。関所は鍵を持たない。authd は判定をしない。関所が乗っ取られても鍵は読めず、authd が乗っ取られても判定と記録は変えられない。
- 2 つとも natsumi のリポジトリではなく、このリポジトリに置く。natsumi の image は全インスタンスで共通で、関所を使わないインスタンスに関所のコードを持ち込まない。
- natsumi の側に残すのは、本人が承認する画面とその窓口、server からの通信を関所に通すための設定である。これは natsumi の ADR が決める。

### 置き場所は、守るインスタンスの Pod の中の別のコンテナ・別の UID

- 関所と authd は、守るインスタンスの Pod の中に、それぞれ別のコンテナとして置く。UID も作業環境・server・互いと別にする。
- 同じ Pod に置くのは、作業環境の通信を同じ network namespace の中で関所へ向け直す（ADR-0002）ためである。
- 作業環境の UID は、関所の決めた口（ADR-0002 の Decision「作業環境の通信は、iptables で関所に向け直す（透過プロキシ）」の向け直しと、作業環境向けの口）にしか届かない。authd と、承認を受け付ける口には届かない。

### 部品の間は Unix socket でつなぎ、相手はカーネルに確かめさせる

- 関所と authd の間、server と関所の間は、それぞれの 2 つのコンテナだけが mount する Unix socket でつなぐ。
- 受ける側は、接続の相手の UID を `SO_PEERCRED` で確かめ、決めた UID 以外を断る。authd は関所の UID だけ、承認を受け付ける口は server の UID だけを受ける。
- 部品の間に共有の秘密（パスワードや token）を置かない。盗まれる秘密が無ければ、作業環境から部品になりすます道も無い。

### 承認を決められるのは本人だけで、会話の外で取る

- 関所は、本人の答え（許す・断る・範囲）を、server の UID からの socket でだけ受け付ける。server は本人の認証の後ろの画面から、その答えを渡す。
- 作業環境と、モデルが呼べるツールには、承認を決める道を渡さない。モデルにできるのは、承認を頼むことと、自分の承認待ちや許しを読むことだけである（ADR-0004）。
- 会話の中の「ok」は、承認として数えない。

### 床は「監視を壊せない」こと。それ以外は自由にさせて記録する

- 関所の役目は、出ていくものをすべて記録し（ADR-0006）、決めていない操作を本人に聞き（ADR-0004）、範囲付きの許しで聞く回数を減らしていくことである。何を許すかの最終の線（床）は関所ではなく、外の仕組みが持つ。
  - Kubernetes は ServiceAccount の RBAC と ValidatingAdmissionPolicy。
  - GitHub は machine account の権限と ruleset（ADR-0005）。
- 床に置くのは、運用の係が関所・authd・監査の記録・監視の仕組みを止めたり書き換えたりできないことである。これは環境の側（RBAC と ValidatingAdmissionPolicy）で守る。
- 断る操作も、関所のコードには固定しない。表のデータとして持ち、環境のリポジトリの変更で変えられる（ADR-0004）。

### 守る対象と、止まったら閉じる（fail closed）

- 守るのは、作業環境が関所を迂回して外へ出られないこと、本物の鍵が authd の外へ出ないこと、承認を本人以外が決められないこと、監視（関所の記録と知らせ）を運用の係が壊せないことである。
- 許す範囲は、表と台帳で通ったもの（ADR-0004）と、外の床（RBAC・GitHub の権限）の内側である。
- 失敗のときは、通さない側に倒す。

- 関所が止まっていれば、関所に向けた通信（作業環境の外向き全部と、server の外の係への通信）は出られない。関所を迂回する道は作らない。
- authd が止まっていれば、鍵の要る通信も鍵の要らない通信も上流へ出られない（関所は上流へ直に出ないため。例外は ADR-0002 の Decision「扱いは宛先ごとに 4 つ」の passthrough）。
- 設定（振り分け・表・操作の定義）が起動のときに読めなければ、関所は起動しない。監査の記録が書けなければ、その要求は通さない（ADR-0006）。

### 適用範囲

- 最初に入れるのは、運用の係のインスタンスだけである。ほかのインスタンスは今の出口（natsumi の ADR 0034・0085）のままで、natsumi の関所に関わる機能は設定で off が既定である。
- 運用の係で形が固まったら、ほかのインスタンスへ広げる。広げるときに変わることがあれば、別の ADR で決める。
- server のモデルの経路と Slack への送信は、関所に通さず今の出口のままにする。

### Muse と違えるところ

- 閉じ込めは VM と `systemd-nspawn` ではなく、Kubernetes の Pod の中のコンテナと UID で作る。今の natsumi の閉じ込めがこの形で、1 インスタンスに 1 つの Pod である。
- プロセスごとの汚れの追跡（tainted egress）はしない。eBPF と LSM の仕組みはこの規模に見合わず、ここではインスタンスごとに分けることで代える。
- connector の処理を cell の外の worker で動かす形（privsep）は取らない。道具は作業環境の中で本物の URL に話し、関所が通信の側で操作に揃える（ADR-0002・ADR-0005）。
- 最初の版には判定器（分類器）を入れない。最初の版で確かめるのは「聞くことと範囲付きの許しで、運用の係に任せられることが増えるか」である。

### 本 ADR で決定しないこと

- 判定器（出ていく文・入ってくる文の injection・操作の意味の判定）の入れ方（委譲先: 次の版の ADR。最初は点数の記録だけで入れ、数日見てから効かせる）。
- natsumi の側の承認の画面・窓口・server の設定の形（委譲先: natsumi の ADR、リポジトリ `yuanying/natsumi` の `docs/adr/`）。
- 関所・authd・監視の部品を守る RBAC と ValidatingAdmissionPolicy の中身（委譲先: 環境のリポジトリの運用の係の配置）。
- クラスタ自体の乗っ取りに気づく仕組み（API server の監査のログ、ログの溜め場、異常の規則）（委譲先: クラスタの監査の作業単位。環境のリポジトリとクラスタの manifest のリポジトリ）。
- 運用の係が作る VM からの外向きの通信と、運用の係の private のリポジトリで動く GitHub Actions。どちらも関所を通らない出口である（委譲先: 本人が別に手当てする。手当てを決めたら別の ADR）。

## Consequences

- 本人に聞く道ができる。表に無い操作は断らずに聞くので、運用の係に任せられることが、許すたびに PR と apply をせずに増えていく。
- 本人の承認は会話の外で取り、関所が確かめる。運用の係が会話で ok を偽っても、操作は通らない。
- 鍵は authd の中にしか無く、関所も作業環境も本物の鍵を見ない。
- 出ていくものはすべて関所の記録に残り、異常に気づく材料になる。
- 部品が増える。Pod のコンテナが 2 つ増え、それぞれの image の版上げとリリースが要る。
- 関所と authd が止まると、運用の係の作業環境は外に出られず、server の外の係への依頼も止まる。止まったことを知らせる仕組み（ADR-0006）に頼る。
- 「自由にさせて気づく」を選んだので、床の外の操作（RBAC で許した範囲の Kubernetes の書き込みなど）は、事後に記録と知らせで気づくことになる。気づく前に起きた変更は、元に戻す作業が要る。
- 判定器が無いので、出ていく文に私事が混ざっても、最初の版の関所は記録するだけで止めない。

## Alternatives Considered

- **今の nginx の中継に、聞く道と台帳を足す**: 中継の判定は nginx の設定とスクリプトで書かれ、状態を持たない。台帳・承認待ち・範囲付きの許しを持たせるには、別のプログラムが要る。
- **関所を natsumi の server の中に作る**: server は作業環境と同じ Pod にあり、モデルを動かす本体でもある。判定と記録を server に置くと、server が乗っ取られたときに監視も一緒に失う。natsumi の image を全インスタンスで共通に保てなくなる。
- **関所を Pod の外（クラスタの共有のプロキシ）に置く**: 作業環境の通信を Pod の外へ向け直すには、CNI や NetworkPolicy の層での向け直しが要る。同じ Pod の中なら、今の出口と同じ iptables の初期化で済む。
- **関所に鍵も持たせる**: 判定と鍵が 1 つのプロセスに集まり、判定の不具合が鍵の漏れに直結する。Muse と同じく分ける。
- **部品の間を TCP と共有の token でつなぐ**: token が漏れれば作業環境から部品になりすませる。Unix socket と `SO_PEERCRED` なら盗まれる秘密が無い。
