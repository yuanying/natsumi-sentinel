# 0002. 作業環境の外向きの通信を透過で関所に通し、宛先ごとに扱いを決める

- Date: 2026-11-09
- Updated: 2026-11-11（IPv6 も向け直すことと、名前解決で AAAA を答える場合を Decision に移した）
- Updated: 2026-11-12（表に無い宛先を本人の許しで通すことを ADR-0008 に移し、振り分けに無い宛先と名前解決の決まりに、その例外を足した）
- Updated: 2026-11-13（関所が上流へ直に送る通信のために、関所の UID の外向きを改めた。ADR-0007）
- Status: Accepted

## Context

関所（ADR-0001）は、作業環境から出ていく通信を見て、判定し、記録する。そのためには、作業環境の通信が必ず関所を通る形が要る。

今の運用の係（クラスタの運用を受け持つ natsumi のインスタンス）の出口は、次の形である。

- Pod の出口の規則は、初期化のコンテナが Pod の network namespace に iptables で 1 度だけ張る。常駐するコンテナは `NET_ADMIN` を持たないので、張った後は誰も書き換えられない。誰の通信かはプロセスの UID で見分ける。
- 作業環境の UID の外向きは、名前解決も含めて全部断る。外へ出るのは loopback の中継（API ごとに 1 つのポート、平文の HTTP）を通るものだけで、中継が鍵を付けて HTTPS で送る（natsumi の ADR 0085）。中継は宛先ごとに通す method と path も絞っている（読むだけの API は GET の決まった path だけ、など）。
- 宛先を 1 つ足すには、中継の server とポートを 1 つ足し、作業環境の道具の設定（kubeconfig の server、`gh` の host など）を loopback のポートに向け直す。道具の手引きにも、宛先ごとのポートを書いている。
- 許可リストに無い宛先への通信は、iptables が黙って落とす。何に出ようとしたかは残らない。
- 運用の係が作る VM と試験用のクラスタには、IPv4 の範囲とポートで直に出られる。そこには関所の持つ鍵が無く、kubectl はそのクラスタの CA で相手を確かめる。

ここで使う言葉は次のとおりである。

- **元の宛先**: 作業環境のプロセスが接続しようとした IP とポート。向け直した後も、カーネルが `SO_ORIGINAL_DST` で教える。
- **振り分け**: 宛先ごとの扱い（下の 3 つ）を決めた設定。表と同じく関所の設定として持つ（ADR-0004 の Decision「設定は、Pod を作り直さずに読み直す」）。

## Decision

### 作業環境の通信は、iptables で関所に向け直す（透過プロキシ）

- 作業環境の UID の外向きの tcp すべてと、名前解決（udp と tcp の 53）を、同じ Pod の関所へ REDIRECT する。規則は今と同じく初期化のコンテナが張り、常駐するコンテナは書き換えられない。
- 関所は、`SO_ORIGINAL_DST` で元の宛先を取り、下の扱いを決める。
- 作業環境の道具は、本物の URL に話す。宛先を足しても、道具の設定もポートも変わらない。作業環境向けの loopback の中継は閉じる。
- 関所の UID の外向きは、authd の socket、passthrough の宛先、名前を引くためのクラスタの DNS だけにする。開く宛先の上流への通信は authd が出す（ADR-0003 の Decision「authd は鍵を持ち、上流へ送る係である」）。
  - 最初の版から、本人が許した表に無い宛先の通信（開いて見るものも passthrough も）を関所が直に送るために、443 も開ける。ループバックとリンクローカルは開けない（2026-11-13、ADR-0007 の Decision「外へ出る道」と ADR-0008）。
  - 次の版から、鍵付きの通信も関所が送るので、関所の UID の外向きを振り分けの開く宛先の上流のポートへ広げ、authd の UID の外向きを token の作り直しに要るものだけに絞る（2026-11-13、ADR-0007）。
- 向け直しで、カーネルは接続の相手の UID を教えない。向け直す元ごとに関所の待ち受けを分け、どこから来た通信かは待ち受けで見分ける。最初の版で向け直すのは作業環境の UID だけである。
- server の外向きは、最初の版では変えない（ADR-0001 の Decision「適用範囲」）。

### IPv6 も同じに向け直す（2026-11-11）

- 作業環境の UID の IPv6 の外向きも、IPv4 と同じく tcp すべてと名前解決を、ip6tables で同じ Pod の関所へ REDIRECT する。関所は、向け直す元ごとに IPv6 の待ち受けも持ち、`IP6T_SO_ORIGINAL_DST` で元の宛先を取る。
- 扱いの決め方は IPv4 と変わらない。開く宛先は名前で決め、authd が名前で引き直してつなぐ（上流へは IPv4 でも IPv6 でもつながる）。passthrough は元の宛先の IP の範囲とポートで決め、範囲は IPv6 でも書ける。
- IPv6 を向け直していない環境（環境の規則が IPv6 を落としているだけのもの）では、関所は今までどおり IPv4 だけを扱う。

透過にするのは、道具の側の協力に頼らないためと、**表に無い宛先へ出ようとしたこと自体を記録と知らせの材料にする**ためである。明示のプロキシでは、プロキシを見ない通信は iptables が黙って落とし、記録に残らない。

### 扱いは宛先ごとに 3 つ

| 扱い | すること |
| --- | --- |
| 開く | 関所の CA で TLS を終端し、要求を読み、宛先の既定と規則で判定し（ADR-0004 の Decision「宛先ごとの既定と規則で、allow・ask・deny を決める」）、記録し、authd に渡して送る |
| passthrough | TLS を開かない。元の宛先の IP の範囲とポートで、通すか断るかを決めて、接続を記録する |
| deny | 通さない。接続を記録する |

- 振り分けに無い宛先は deny にする。ただし、台帳に本人の宛先の許しがあれば、その許しの扱い（開く、または passthrough）で通す（2026-11-12、ADR-0008 の Decision「表に無い宛先も、本人が許せば通る」）。
- 開く宛先ごとに、規則に当たらない要求の既定（allow・ask・deny）と、任意の規則（method・path などから操作へ）を持つ。読むだけの宛先は「GET は allow、ほかは deny」と書ける。判定の細部は ADR-0004 が決める。
- 開く宛先は HTTP だけを扱う。HTTP でない通信は、passthrough の宛先でしか通らない。
- passthrough は、関所が鍵を持たず、相手を作業環境の側で確かめる宛先に使う（運用の係が作る VM と試験用のクラスタ）。中身を見られないので、記録は宛先・ポート・量・時間までになる。

### TLS は関所の CA で終端する

- 開く宛先の TLS は、関所が終端する。関所は、接続の SNI の名前ごとに、関所の CA で署名した証明書をその場で作って見せる。
- 関所の CA の秘密鍵は、関所にだけ mount する。作業環境は、CA の証明書（秘密ではない）を信用する。
- 関所が中身を読んだ要求は、authd が上流へ新しい TLS で送り、上流の証明書を確かめる（ADR-0003 の Decision「authd は鍵を持ち、上流へ送る係である」）。宛先の許しの要求は最初の版から、ほかの要求は次の版から、関所の上流へ送る部品が同じに送って確かめる（2026-11-13、ADR-0007）。

### 名前で決め、名前を引き直してつなぐ

- 開く宛先は、TLS の SNI と HTTP の Host の名前で決める。2 つの名前が違えば断る。
- SNI の無い TLS（IP を直に書いた URL など）と、Host の無い HTTP は、名前が取れないので断る。道具には名前で宛先を書かせる（kubeconfig の server も名前で書く）。
- 上流へつなぐ先は、その名前を引き直して決める。元の宛先の IP は使わない。関所は判定した名前を authd に渡し、authd はその名前でつなぐ（ADR-0003 の Decision「authd は鍵を持ち、上流へ送る係である」）。作業環境が名前と IP を食い違わせても、関所が決めた名前の本物の宛先にしか届かない。
- passthrough は、元の宛先の IP の範囲で決める。名前は使わない。宛先の許しで passthrough にした名前だけは、SNI の名前で決め、その名前を引き直してつなぐ（2026-11-12、ADR-0008 の Decision「許した宛先の扱い: 既定は開いて見る。passthrough も選べる」）。

### 名前解決は関所が受け、振り分けにある名前だけに答える

- 作業環境の名前解決は関所が受ける。振り分けにある名前と、台帳に宛先の許しのある名前には本物の IP を答え、それ以外には NXDOMAIN を答える（宛先の許しは 2026-11-12、ADR-0008 の Decision「表に無い宛先も、本人が許せば通る」）。許されていない名前は、上流の DNS に問い合わせない。問い合わせはすべて記録し、断った名前は知らせの材料にする（ADR-0006）。
- AAAA に本物の IPv6 を答えるのは、その向け直し元の IPv6 を関所に向け直しているときだけである（2026-11-11）。向け直していなければ、AAAA には答えを返さない。答えれば、道具が関所を通らない IPv6 の宛先を試すことになる。
- IPv6 を向け直しているとき、片方の型のアドレスだけを持つ名前には、もう片方の型の問い合わせに答えの無い NOERROR を返す（名前はある）。どちらも無ければ NXDOMAIN である。こうして IPv4 を持たない名前の宛先にも届く。
- 作業環境が関所に話すための固定の名前（作業環境向けの口）も、関所が答える。
- 道具は名前を引けなければ動かないので、名前解決の窓口は守りとは別に機能として要る。

### ssh

- ssh は中身を読めないので、関所では開かない。GitHub への git は HTTPS で話す（ADR-0005 の Decision「git の push」）。
- VM と試験用のクラスタへの ssh は passthrough で通る。ssh の秘密鍵は今の ssh-agent のコンテナのままにする。

### 切り替えの後も、中継へ戻せるようにしておく

- 作業環境の出口は、1 度に全部を関所に切り替える。中継と透過を並べると、道具の手引きが 2 通りになるためである。
- 切り替えの後もしばらくは、環境のリポジトリの変更だけで今の中継の出口に戻せる配置を残す。関所は fail closed で、運用の係は本番を扱うので、関所の不具合で運用の係が止まったときに戻す道が要る。
- この配置は、関所で作業環境の出口を動かして本人が戻す道は要らないと判断し、環境のリポジトリからそれを消すまで残す。

### 守る対象と、倒す向き

- 守るのは、鍵の要る通信が関所を通らずに行えないことと、作業環境が名前や IP を細工しても、関所が決めた名前の本物の宛先にしか鍵が届かないことである。
- 持ち出しは防がない。passthrough の先の VM から外へ出られるあいだは、関所を迂回して外へ出す道が残る（ADR-0001 の Decision「関所が守るもの」）。
- 向け直しの規則を張れなければ、初期化のコンテナは失敗し、Pod は起動しない（今の出口の規則と同じ）。
- 関所が止まっていれば、向け直した通信は出られない（ADR-0001 の Decision「止まったら閉じる（fail closed）」）。
- 振り分けが読めない・壊れているときの扱いは、表と同じく ADR-0004 の Decision「設定は、Pod を作り直さずに読み直す」に従う。

### 本 ADR で決定しないこと

- 関所が扱う HTTP の版（HTTP/1.1・HTTP/2）と、upgrade（WebSocket など）の扱い（委譲先: 関所の実装の PR。upgrade を通すときも、通すかどうかは判定と記録の後にする）。
- 証明書の作り方と寿命、CA の鍵の入れ替えの手順（委譲先: 関所の実装の PR と、環境のリポジトリの運用手順）。
- IPv6 の向け直しの規則の中身（委譲先: 環境のリポジトリの初期化のコンテナ。関所の側で要るものは関所の仕様書 `docs/redirect.md`）。向け直すことと AAAA を答える場合は、2026-11-11 に Decision へ移した。
- 振り分けの中身（どの宛先をどの扱いにするか）と、作業環境に CA を信用させる設定、中継へ戻す配置の形（委譲先: 環境のリポジトリの運用の係の配置）。
- 振り分けの形式（委譲先: 関所の設定の仕様書）。
- server の外向きを関所に通すときの向け直しの選び方（委譲先: 判定器を入れる版の ADR）。

## Consequences

- 道具は本物の URL と、ふつうの設定（kubeconfig・`gh`・git）で動く。宛先を足すのは振り分けの 1 行で、道具の設定もポートも変えない。道具の手引きから宛先ごとのポートが消える。
- 作業環境の通信はすべて関所を通り、記録に残る。表に無い宛先へ出ようとしたことも、名前解決で何を引こうとしたかも残る。
- 名前で引き直してつなぐので、作業環境が DNS の答えや IP を細工しても、振り分けにある名前の本物の宛先にしか鍵は届かない。
- 作業環境は関所の CA を信用する。関所の CA の鍵が漏れれば、その Pod の中の TLS は読める。CA の鍵は関所にだけ置き、関所の外へ出さない。
- 証明書を確かめる相手を自分で指定する道具（独自の CA を埋め込んだもの、証明書を固定するもの）は、開く宛先では動かない。そういう宛先は passthrough にするしかなく、中身は記録できない。
- IP を直に書いた URL は使えない。道具の設定を名前で書く必要がある。IPv6 のアドレスを直に書いた URL も同じである。
- IPv6 を向け直す環境では、作業環境の規則と関所・authd の UID の外向きを IPv4 と IPv6 の両方で持つ。片方だけを開けると、そちらの型の宛先には届かない。
- passthrough の宛先（VM・試験用のクラスタ）の中で何をしたかは、関所からは見えない。宛先と量だけが残る。
- 関所が止まると、作業環境の外向きはすべて止まる。戻す配置を残すあいだは、中継の設定も環境のリポジトリに残り続ける。

## Alternatives Considered

- **今のように宛先ごとの loopback のポートに話させる（明示のプロキシ）**: 宛先を足すたびに、ポートと中継と道具の設定を足すことになる。許可リストの外への通信は黙って落ち、記録に残らない。
- **`HTTPS_PROXY` で関所を指す**: 環境変数を見ない道具や、作業環境の外から渡せない設定がある。プロキシを見ない通信は記録に残らない。
- **inspect（開いて操作で判定）と inject（開いて鍵だけ）を別の扱いにする**: inject は操作を 1 つも定義していない inspect と同じで、違いは規則に当たらない要求の既定だけである。分けると、読むだけの宛先に任意の method・path が鍵付きで通ることが見えにくくなる。
- **作り物の IP を答え、接続の先で名前に戻す（Muse の形）**: 関所が名前と作り物の IP の対応を持ち続けることになり、TTL の切れ目で対応が崩れる。SNI と Host で名前が取れるので、本物の IP を答えて名前で引き直せば足りる。
- **作業環境にクラスタの DNS を開ける**: 何を引いたかが関所の記録に残らない。
- **元の宛先の IP にそのままつなぐ**: 作業環境が名前と IP を食い違わせれば、許した名前のふりをして別の宛先（クラスタの内側を含む）に鍵を運べる。
- **IPv4 を持たない名前にだけ、関所へ向け直される作り物の IPv4 を 1 つ答える（2026-11-11）**: 名前は SNI と Host で取れるので、名前と IP の対応を持たずに済み、IPv6 の向け直しも要らない。しかし、作業環境の IPv6 が関所を通らない元の穴が残り、「振り分けにある名前には本物の IP を答える」に例外ができる。配置の工夫を関所の中の工夫に置き換えるだけになるため、退けた。
- **中継と関所を並べて少しずつ移す**: 道具の手引きと設定が 2 通りになり、どちらを使ったかで記録の残り方が変わる。
