# 0002. 作業環境の外向きの通信を透過で関所に通し、宛先ごとに扱いを決める

- Date: 2026-11-09
- Status: Accepted

## Context

関所（ADR-0001）は、作業環境から出ていく通信を見て、判定し、記録する。そのためには、作業環境の通信が必ず関所を通る形が要る。

今の運用の係（クラスタの運用を受け持つ natsumi のインスタンス）の出口は、次の形である。

- Pod の出口の規則は、初期化のコンテナが Pod の network namespace に iptables で 1 度だけ張る。常駐するコンテナは `NET_ADMIN` を持たないので、張った後は誰も書き換えられない。誰の通信かはプロセスの UID で見分ける。
- 作業環境の UID の外向きは、名前解決も含めて全部断る。外へ出るのは loopback の中継（API ごとに 1 つのポート、平文の HTTP）を通るものだけで、中継が鍵を付けて HTTPS で送る（natsumi の ADR 0085）。
- 宛先を 1 つ足すには、中継の server とポートを 1 つ足し、作業環境の道具の設定（kubeconfig の server、`gh` の host など）を loopback のポートに向け直す。道具の手引きにも、宛先ごとのポートを書いている。
- 運用の係が作る VM と試験用のクラスタには、IPv4 の範囲とポートで直に出られる。そこには関所の持つ鍵が無く、kubectl はそのクラスタの CA で相手を確かめる。

ここで使う言葉は次のとおりである。

- **元の宛先**: 作業環境のプロセスが接続しようとした IP とポート。向け直した後も、カーネルが `SO_ORIGINAL_DST` で教える。
- **振り分け**: 宛先ごとの扱い（下の 4 つ）を決めた表のデータ。関所の設定として持つ（ADR-0004）。

## Decision

### 作業環境の通信は、iptables で関所に向け直す（透過プロキシ）

- 作業環境の UID の外向きの tcp すべてと、名前解決（udp と tcp の 53）を、同じ Pod の関所へ REDIRECT する。規則は今と同じく初期化のコンテナが張り、常駐するコンテナは書き換えられない。
- server の UID の通信のうち、外の係（A2A のエージェント）の宛先への 443 も関所へ向け直す。server のほかの外向き（モデルの経路、Slack）は今の出口のままにする。
- 関所は、`SO_ORIGINAL_DST` で元の宛先を取り、下の扱いを決める。
- 作業環境の道具は、本物の URL に話す。宛先を足しても、道具の設定もポートも変わらない。作業環境向けの loopback の中継は閉じる。
- 関所の UID の外向きは、authd の socket、passthrough の宛先、名前を引くためのクラスタの DNS だけにする。inspect と inject の上流への通信は authd が出す（ADR-0003）。

### TLS は関所の CA で終端する

- inspect と inject の宛先の TLS は、関所が終端する。関所は、接続の SNI の名前ごとに、関所の CA で署名した証明書をその場で作って見せる。
- 関所の CA の秘密鍵は、関所にだけ mount する。作業環境と server は、CA の証明書（秘密ではない）を信用する。
- 関所が中身を読んだ要求は、authd が上流へ新しい TLS で送り、上流の証明書を確かめる（ADR-0003）。

### 扱いは宛先ごとに 4 つ

| 扱い | すること |
| --- | --- |
| inspect | TLS を開き、要求を操作に揃えて表で判定し（ADR-0004）、記録し、authd に渡して鍵を付けて送る |
| inject | TLS を開き、記録し、authd に渡して鍵を付けて送る。操作の判定はしない |
| passthrough | TLS を開かない。元の宛先の IP の範囲とポートで、通すか断るかを決めて、接続を記録する |
| deny | 通さない。接続を記録する |

- 振り分けに無い宛先は deny にする。
- inspect と inject は HTTP だけを扱う。HTTP でない通信は、passthrough の宛先でしか通らない。
- passthrough は、関所が鍵を持たず、相手を作業環境の側で確かめる宛先に使う（運用の係が作る VM と試験用のクラスタ）。中身を見られないので、記録は宛先・ポート・量・時間までになる。

### 名前で決め、関所が名前を引き直してつなぐ

- inspect と inject は、TLS の SNI と HTTP の Host の名前で宛先を決める。2 つの名前が違えば断る。
- 上流へつなぐ先は、その名前を引き直して決める。元の宛先の IP は使わない。関所は判定した名前を authd に渡し、authd はその名前でつなぐ（ADR-0003）。作業環境が名前と IP を食い違わせても、関所が決めた名前の本物の宛先にしか届かない（SSRF にならない）。
- passthrough は、元の宛先の IP の範囲で決める。名前は使わない。

### 名前解決は関所が受け、振り分けにある名前だけに答える

- 作業環境の名前解決は関所が受ける。振り分けにある名前には本物の IP を答え、それ以外には NXDOMAIN を答える。問い合わせはすべて記録する（ADR-0006）。
- 作業環境が関所に話すための固定の名前（作業環境向けの口）も、関所が答える。
- 作り物の IP を答えて接続の先で名前に戻す形と、作業環境にクラスタの DNS を直に開ける形は取らない（Alternatives Considered）。

### ssh

- ssh は TLS でなく中身も読めないので、関所では扱わない。GitHub への git は HTTPS で話す（ADR-0005）。
- VM と試験用のクラスタへの ssh は passthrough で通る。ssh の秘密鍵は今の ssh-agent のコンテナのままにする。

### 守る対象と、倒す向き

- 守るのは、作業環境から関所を迂回して外へ出る道が無いことである。迂回の道があれば、記録も判定も効かない。
- 向け直しの規則を張れなければ、初期化のコンテナは失敗し、Pod は起動しない（今の出口の規則と同じ）。
- 関所が止まっていれば、向け直した通信は出られない（ADR-0001）。
- 振り分けが読めない・壊れているときの扱いは、表と同じく ADR-0004 に従う。

### 本 ADR で決定しないこと

- 関所が扱う HTTP の版（HTTP/1.1・HTTP/2）と、upgrade（WebSocket など）の扱い（委譲先: 関所の実装の PR。upgrade を通すときも、通すかどうかは判定と記録の後にする）。
- 証明書の作り方と寿命、CA の鍵の入れ替えの手順（委譲先: 関所の実装の PR と、環境のリポジトリの運用手順）。
- IPv6 の向け直しの規則と、名前解決で AAAA を答えるか（委譲先: 関所の実装の PR と、環境のリポジトリの初期化のコンテナ）。
- 振り分けの中身（どの宛先をどの扱いにするか）と、作業環境・server が CA を信用させる設定（委譲先: 環境のリポジトリの運用の係の配置）。
- 振り分けの形式（委譲先: 関所の設定の仕様書）。

## Consequences

- 道具は本物の URL と、ふつうの設定（kubeconfig・`gh`・git）で動く。宛先を足すのは振り分けの 1 行で、道具の設定もポートも変えない。道具の手引きから宛先ごとのポートが消える。
- 作業環境の通信はすべて関所を通り、記録に残る。名前解決も記録に残るので、何を引こうとしたかも見える。
- 名前で引き直してつなぐので、作業環境が DNS の答えや IP を細工しても、振り分けにある名前の本物の宛先にしか届かない。
- 作業環境と server は関所の CA を信用する。関所の CA の鍵が漏れれば、その Pod の中の TLS は読める。CA の鍵は関所にだけ置き、関所の外へ出さない。
- 証明書を確かめる相手を自分で指定する道具（独自の CA を埋め込んだもの、証明書を固定するもの）は、inspect と inject の宛先では動かない。そういう宛先は passthrough にするしかなく、中身は記録できない。
- passthrough の宛先（VM・試験用のクラスタ）の中で何をしたかは、関所からは見えない。宛先と量だけが残る。
- 関所が止まると、作業環境の外向きはすべて止まる。

## Alternatives Considered

- **今のように宛先ごとの loopback のポートに話させる（明示のプロキシ）**: 宛先を足すたびに、ポートと中継と道具の設定を足すことになる。いまの「1 つ許すたびに PR と apply」の手間が残る。
- **`HTTPS_PROXY` で関所を指す**: 環境変数を見ない道具や、作業環境の外から渡せない設定がある。透過にすれば、道具の側の協力に頼らない。
- **作り物の IP を答え、接続の先で名前に戻す（Muse の形）**: 関所が名前と作り物の IP の対応を持ち続けることになり、TTL の切れ目で対応が崩れる。SNI と Host で名前が取れるので、本物の IP を答えて名前で引き直せば足りる。
- **作業環境にクラスタの DNS を開ける**: DNS の問い合わせに中身を載せて外へ出す道になり、何を引いたかも関所の記録に残らない。
- **元の宛先の IP にそのままつなぐ**: 作業環境が名前と IP を食い違わせれば、許した名前のふりをして別の宛先（クラスタの内側を含む）に届く。
