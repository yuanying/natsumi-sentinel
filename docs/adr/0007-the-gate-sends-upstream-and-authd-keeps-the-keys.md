# 0007. 関所が判定して自分で上流へ送り、authd は鍵を保管して要求ごとに渡す

- Date: 2026-11-13
- Status: Accepted

## Context

今の形（ADR-0001・ADR-0003）では、関所と authd の役目は次のとおりである。

- 関所は、作業環境の通信を受け、判定し、記録する。開く宛先の要求は、サロゲートを付けたまま authd に渡す。関所は本物の鍵を見ず、上流へは直に出ない（例外は振り分けの passthrough）。
- authd は、開く宛先の上流へのすべての通信を送る。鍵の要らない宛先も authd が送る。名前を引き直し、上流の証明書を確かめ、登録と合うサロゲートだけを本物の鍵に差し替える。
- 2 つを分けて守れるのは、**鍵の値が、作業環境から来た敵意のある入力を解く関所のプロセスに無い**ことである（ADR-0001 の Decision「関所と authd を、natsumi とは別のプログラムとして作る」）。設計の見直しでも、分けるのに掛かる費用は小さいので、分けたままでよいとされた。

表に無い宛先を本人の許しで通す（ADR-0008）には、authd の登録に無い名前へ送る道が要る。今の形のままでは、authd に「登録の外の名前へ、鍵を付けずに公のアドレスへ送る」例外を足し、passthrough の宛先の許しのために関所の UID にも公のアドレスの 443 を開けることになる。外へ出るプロセスは、宛先の種類によって authd と関所に分かれたままになる。

本人は、出口をどちらか 1 つに寄せたい。寄せるなら、Meta が公開している Muse の形に寄せたい。Muse の記事は、Sentinel が、サロゲートを authd から受け取った本物の資格情報に、ネットワークの境界で差し替えると書いている。authd は資格情報を保管し、代理の token を作る。Sentinel が本物を持ち続けるのか、外へつなぐのがどのプロセスかは、記事に書かれていない。

本人は、この形に寄せると ADR-0001 の「鍵の値が関所のプロセスに無い」が言えなくなり、乗っ取られた関所から本物の鍵が漏れうると聞いたうえで、寄せることを選んだ。この ADR は、その出口の形と、鍵の分離の代わりに守ること、移す順番を決める。

ここで使う言葉は次のとおりである。ADR-0003 の言葉（本物の鍵・サロゲート・置き場所）はそのまま使う。

- **鍵付きの通信**: 登録したサロゲートを本物の鍵に差し替えて送る通信。
- **上流へ送る部品**: 関所の中で、判定を済ませた要求を上流へ送る部分。名前の引き直し、つなぐ先の確かめ、TLS と証明書の確かめ、送ることを受け持つ。

## Decision

### 関所が判定し、差し替え、自分で上流へ送る。authd は鍵の保管係として残る

- 関所は、通すと決めた要求を、自分で上流へ送る。
- 鍵付きの通信では、関所は要求ごとに、見つけたサロゲートと置き場所と宛先の名前の組で authd に頼む。authd が本物の鍵を返したら、関所はそれに差し替えて送る。
- authd は、鍵の正本（mount した Secret のファイルなど）と、登録（サロゲート・置き場所・上流の名前の組）を持つ。寿命の短い token の作り直しも authd に残す。鍵付きの通信を関所へ移した版から、authd は上流へ送らない。
- 道具にサロゲートを持たせること（ADR-0003 の Decision「道具には、いつもサロゲートを持たせる」）と、本文は探さず、ヘッダと query だけを差し替えることは変えない。
- authd へは、今までどおり関所の UID からしか届かない（ADR-0001 の Decision「部品の間は Unix socket でつなぎ、相手はカーネルに確かめさせる」）。

### 鍵の分離の代わりに守ること

- **関所は鍵を持ち続けない。** 本物の鍵は要求ごとに受け取り、その要求の差し替えにだけ使い、送り終えたら捨てる。溜めず、ディスクに書かず、記録にもエラーの文にも出さない。
- **authd は、登録と合う組にしか鍵を渡さない。** サロゲートの使い道の上流の名前と置き場所が登録と合うときだけ渡し、合わなければ断る（今の差し替えの決まりと同じ確かめ）。
- authd の側に、渡したことの記録を別に残すことはしない。authd を小さく保つためである。

### 守れなくなること

- 乗っ取られた関所は、登録どおりの組で authd に頼んで本物の鍵を受け取り、それを別の宛先へ送れる。authd は、関所が実際にどこへ送ったかを確かめられない。
- authd は渡したことを記録しないので、乗っ取られた関所が鍵を受け取って持ち出しても、関所の外に手がかりは残らない。
- ADR-0001 の「鍵の値が、関所のプロセスに無い」は、鍵付きの通信を関所へ移した版から言えなくなる。それまで（下の最初の版）は今のまま言える。
- 変わらずに言えることは次のとおりである。作業環境は本物の鍵を見ない。鍵の正本は authd にだけ mount する。authd へは関所からしか届かない。関所が持つのは、送っている要求の鍵だけである。

### 移す順番

- **最初の版は、本人が許した表に無い宛先（ADR-0008）の通信だけを、関所が直に送る。** これらは鍵の付かない通信である。
- 鍵付きの通信と、振り分けで開く鍵の要らない宛先の通信は、最初の版では今のまま authd が送る。最初の版のあいだ、外へ出るプロセスは authd と関所の 2 つになる。
- 鍵付きの通信を関所へ移すのは、次の版である。関所自身の問い合わせ（ADR-0005 の対象の引き直し）も、次の版から同じ受け取り方で関所が送る。
- **いま本番で動いているのは、今の形（authd が送る）である。** 最初の版で変わるのは、宛先の許しの通信だけである。
- 最初の版で関所に作る上流へ送る部品は、次の版でそのまま鍵付きの通信に使う。最初に本番の鍵付きの経路に触らずに、その部品を宛先の許しの通信で試すためである。

### 上流へ送る部品が守ること

上流へ送る部品は、今 authd が守っていること（ADR-0003 の Decision「authd は鍵を持ち、上流へ送る係である」）を同じに守る。

- 関所が判定した名前を引き直してつなぐ。元の宛先の IP は使わない（ADR-0002 の Decision「名前で決め、名前を引き直してつなぐ」）。
- 上流の証明書を、その名前で確かめる。
- リダイレクトをたどらない。別の名前へ飛ぶ応答は、そのまま作業環境に返り、その先への要求はまた判定に掛かる。
- サロゲートのまま上流へ送らない。登録したサロゲートが、差し替えない要求（宛先の許しの通信など）や、差し替えた後のヘッダと query に残っていれば、その要求を断る。
- 宛先の許しの通信は、引いたアドレスがループバックかリンクローカルならつながない。私用の範囲には、内側のドメインの一覧の名前だけをつなぐ（ADR-0008）。鍵付きの通信の上流は、登録と振り分けで決まるので、この確かめとは別である。
- 実際につないだアドレスを記録に残す（ADR-0006 の改め）。

### 外へ出る道

- 最初の版では、関所の UID の外向きに、宛先の許しの通信のための 443 を足す（ループバックとリンクローカルは落とす）。authd の UID の外向きは変えない。
- 次の版では、関所の UID の外向きを、振り分けの開く宛先の上流のポートへ広げる。authd の UID の外向きは、寿命の短い token の作り直しに要る宛先だけに絞る。
  - 今の authd は、kubelet が作り直す token のファイルを読み直すだけで、作り直しのために外へは出ない。この形のままなら、次の版で authd の UID の外向きは閉じられる。
- 今ある振り分けの passthrough（運用の係が作る VM と試験用のクラスタへの、IP の範囲とポートで決めるもの）は変えない。
- iptables は名前で絞れないので、どの名前へつなぐかは、今の authd と同じく関所の中で確かめる。

### 止まったときと、倒す向き

- 最初の版では、authd が止まると、鍵付きの通信と振り分けの開く宛先の通信は今までどおり止まる。宛先の許しの通信は authd を使わないので止まらない。関所が止まれば、すべて止まる。
- 次の版では、authd が止まるか鍵を渡さなければ、関所はその鍵付きの要求を断る。サロゲートのまま送ることはしない。鍵の要らない要求は止まらない。
- 上流につなげない、証明書を確かめられない、つながないアドレス（宛先の許しのループバック・リンクローカルと、外の名前の私用の範囲）のときは、送らない側に倒す。

### 記録と指標

- 記録は今までどおり関所が書き、authd は書かない（ADR-0006 の Decision「何を残すか」）。
- 関所が直に送った要求が上流に届かなかったときは、今 authd が返している失敗と同じ分け方（つなげない・証明書・そのほか）で、関所が理由を記録に残す。
- 次の版で authd が鍵を渡さなかったときは、今の authd の断りと同じく、authd が返した理由を関所が記録に残す。authd は断った数を指標に出す。

### 適用範囲

- 対象は、運用の係のインスタンスの作業環境の出口だけである（ADR-0001 の Decision「適用範囲」）。

### 本 ADR で決定しないこと

- 次の版の細部: authd が関所に本物の鍵を渡す口の形、受け取った鍵を関所のメモリでどう扱うか、関所がサロゲートと置き場所と上流の CA を知るための登録の形の変更、記録と指標の欄と名前（委譲先: 鍵付きの通信を関所へ移す版の実装の PR と、`docs/authd-protocol.md`・`docs/authd-registration.md`）。
- 最初の版で、関所が登録したサロゲートの値を知る形（委譲先: 宛先の許しの実装の PR）。
- 関所が直に送った要求の失敗の理由の名前と、作業環境に返す応答の形（委譲先: 宛先の許しの実装の PR と `docs/gate-responses.md`）。
- 次の版を本番に入れる時期（委譲先: 本人。様子見の期間は置かず、次の版の実装が終わったらすぐ移す。本番の切り替えは、そのつど本人が承認する）。
- 環境の側の規則の中身（委譲先: 環境のリポジトリの運用の係の配置）。

## Consequences

- 出口は、次の版から関所 1 つになる。上流へ送る部品が 1 つになり、名前の引き直し・証明書の確かめ・リダイレクトの扱いが 1 か所で決まる。
- 宛先の許しのために、authd の登録の外の名前へ送る例外を authd に足さずに済む。authd は登録の確かめと鍵の保管に縮み、次の版から上流へつなぐコードを持たなくなる。
- 次の版から、乗っ取られた関所は本物の鍵を受け取って持ち出せる。それは記録にも authd にも残らない。関所を乗っ取られにくく保つこと（入力を解く部分を小さく、表のデータで決める）の重みが増す。
- 最初の版のあいだは、外へ出るプロセスが authd と関所の 2 つになる。関所の UID は 443 に出られるので、乗っ取られた関所は、鍵の付かない要求を、環境の側の規則が許す範囲のどこへでも送れる。持ち出しは今も防いでいない（ADR-0001 の Decision「関所が守るもの」）。
- 最初の版では、本番の鍵付きの経路は変わらない。上流へ送る部品の不具合は、宛先の許しの通信にしか効かない。
- 鍵付きの通信を移すまで、上流へ送る仕組みが authd と関所の 2 つに並ぶ。どちらにも同じ守り（引き直し・証明書・リダイレクト・サロゲートのまま送らない）を保つ必要がある。

## Alternatives Considered

- **authd をなくし、関所が鍵も持つ**: 1 つのプロセスで済むが、鍵の正本と token の作り直しの権限が、敵意のある入力を解くプロセスに常に載る。要求ごとに受け取って捨てる形なら、関所が持つのは送っている要求の鍵だけになる。Muse も authd を保管係として残している。
- **authd に寄せて鍵の分離を保つ（宛先の許しの通信も authd が送り、passthrough も authd が TCP で中継する）**: ADR-0001 の分離は保てるが、authd に登録の外の名前へ送る例外と TCP の中継が増え、authd が小さくなくなる。出口を 1 つに寄せたい本人の方針に、関所ではなく authd の側で寄せることになり、Muse の形から離れる。
- **authd の側に、鍵を渡した記録を別に残す**: 乗っ取られた関所が鍵を受け取ったことの手がかりが関所の外に残るが、authd に記録の置き場と書けないときの倒し方が要り、authd を小さく保てない。
- **関所が受け取った鍵を溜めて使い回す**: authd への頼みが減るが、乗っ取られたときに関所の中にある鍵が増える。鍵のファイルの入れ替えも関所が追うことになる。
- **鍵付きの通信も最初の版で一度に移す**: 出口が 2 つになる間が無くなるが、最初の版で本番の鍵付きの経路を変えることになる。上流へ送る部品を鍵の付かない通信で先に試せない。
