# 0004. 宛先ごとの規則で決め、決めていないものは本人に聞き、範囲付きの許しを台帳に残す

- Date: 2026-11-09
- Updated: 2026-11-12（表に無い宛先への本人の許し（宛先の許し）を、台帳・許しの範囲・先に頼む口に足した。ADR-0007）
- Status: Accepted

## Context

今の運用の係（クラスタの運用を受け持つ natsumi のインスタンス）の出口の判定は、中継のスクリプトの許可リストである。結果は「通す」と「403」だけで、次のことが起きている。

- 許可リストに無い操作は断られる。本人が「その場だけやってほしい」と思っても、通す道は許可リストを書き換えることしかない。
- 許可リストを書き換えるには、環境のリポジトリの PR・テスト・apply が要り、中継の設定が変わるので Pod も作り直される。
- natsumi にある本人の承認は、Slack への投稿の承認（natsumi の ADR 0041）だけで、1 件ずつで範囲が無い。運用の係のマージの ok は会話の中で取っていて、中継は確かめられない。

関所（ADR-0001）は、ここに「聞く」と「許しを覚える」を足す。ここで使う言葉は次のとおりである。

- **操作**: 要求を、人が読める意味に揃えたもの。名前と対象を持つ（例: GitHub の PR のマージ、対象はリポジトリと PR の番号）。要求を操作に揃えるのは、宛先ごとの規則と、要るときは宛先に固有の **コネクタ** である。GitHub のコネクタは ADR-0005 が決める。
- **生の操作**: どの規則にも当たらない要求。名前の代わりに宛先と method と path を持つ。
- **表**: 宛先ごとの既定と、操作ごとの allow・ask・deny。
- **承認待ち**: ask になった要求。本人の答えを待つ。
- **許し**: 本人が承認待ちに答えて出したもの。範囲（下の節）を持ち、**台帳** に残る。

## Decision

### 宛先ごとの既定と規則で、allow・ask・deny を決める

- 開く宛先（ADR-0002 の Decision「扱いは宛先ごとに 3 つ」）ごとに、次を持つ。
  - **規則**: 要求（method・path など。GitHub はコネクタが読んだ欄も）から操作へ揃える対応と、操作ごとの allow・ask・deny。規則は任意で、無い宛先もある。
  - **既定**: どの規則にも当たらない要求の扱い（allow・ask・deny）。
- allow は通す。ask は承認待ちにする（台帳に当てはまる許しがあれば通す）。deny は断る。
- 最初の版の宛先の形は次のとおりである。

| 宛先 | 規則 | 既定 |
| --- | --- | --- |
| GitHub の API と git | ADR-0005 の操作の対応 | ask |
| Kubernetes の API | 無し。許す範囲は ServiceAccount の RBAC が決め、関所は鍵と記録を受け持つ | allow |
| 読むだけの API（gated の後ろの一覧の API など） | GET を allow | deny |
| 鍵の要らない置き場（言語のパッケージなど） | GET を allow | deny |

- Kubernetes の API を操作に揃えないのは、許す範囲を RBAC で書けるからである。RBAC で書けない操作（多くの要求で 1 つの意味になるもの）が要るようになったら、そのときにコネクタを足す。
- 読むだけの宛先の「GET だけ」は、今の中継が宛先ごとに method と path を絞っていたことに当たる。path までは絞らず、method で読みに限る。

### 決めていないものは本人に聞く

- 既定が ask の宛先では、規則に当たらない要求を断らずに本人に聞く。
  - 操作に揃うが表に行が無いもの: その操作として ask にする。
  - どの操作にも揃わないもの: 生の操作として ask にする。出せる範囲は、1 回と、同じ宛先・method・path への期限付きまでとする。
- 生の操作に名前を付けて育てるのは、環境のリポジトリの規則の変更である（読み直しで効く）。
- **deny も表のデータである。** 関所のコードに「いつも断る」操作を置かない。断っている操作も、環境のリポジトリの変更で ask や allow に変えられる。
  - deny の操作は、承認の画面からは通せない。その場だけ通したいなら、本人が自分で操作するか、表を ask に変える。
  - 表が後から deny に変わったら、その操作にある許しより deny が勝つ。
  - deny で断るときは、本文に「表で断っている。変えるには本人が表を直す」ことを書く。

### 許しの範囲は「1 回」と「期限付き」の 2 つ

- **1 回**: 承認待ちになった要求の中身の指紋（method・path・本文や、操作の対象と引数）に 1 度だけ当てはまる。使ったら消える。使われなくても、短い期限が来たら消える。
- **期限付き**: 範囲は「操作 × 対象（リポジトリ・名前空間・node など）」。期限は本人が選ぶ。期限の無いもの（「ずっと」）は、期限付きの選択肢の 1 つとして扱う。
- 承認待ちごとに、出せる範囲の選択肢を関所が示す。natsumi の承認の画面は、それを並べるだけにする。選択肢の値は関所の設定で決め、最初は 1 時間・1 日・30 日・期限なしとする。
- 範囲は、操作の種類で絞らない。危ない操作は表の既定が deny なので、範囲が効くのは本人が ask にした操作だけである。
- session と「この用件」（きっかけのアラートや PR）の範囲は入れない。用件はモデルの申告で、偽れるためである。
- 効いている許しは、本人が承認の画面で一覧し、取り消せる。期限が切れたか取り消したら、台帳から消える。
- 表に無い宛先への許し（宛先の許し）は、期限付きだけで、1 回は置かない。範囲は名前かドメインの下で、操作 × 対象ではない（2026-11-12、ADR-0007 の Decision「許しの単位と期限」）。

### ask はすぐ 403 で返し、答えは会話の外から届ける

- ask の要求は、接続を開けたまま待たない。すぐに 403 で返し、本文に承認待ちの id・操作・「許されたら同じ要求をやり直して」を書く。
- 関所が作った応答（ask と deny の 403、断りの文）には、関所の応答だという決まった印を付ける。上流の応答に同じ印があれば、関所が取り除く。上流（GitHub など）が返す 403 と、関所の 403 を見分けられるようにするためである。
- git のように 403 の本文を見せない道具では、承認待ちの id は、下の「自分の状態を読む」口で知る。
- 本人の答えは、server の窓口（ADR-0001 の Decision「承認を決められるのは本人だけで、会話の外で取る」の口）から関所に届く。関所は答えが出たことを server に知らせ、server がモデルに知らせる（知らせ方は natsumi の ADR 0096）。
- 運用の係が同じ要求をやり直すと、台帳の許しに当たって通る。

### 先に頼めるのは、具体的な操作と対象の一覧だけ

- 運用の係は、要求を出す前に承認を頼める。頼めるのは、具体的な操作と対象の一覧（マージする PR の番号と head の SHA など）を、1 回の許しの束として 1 つの承認待ちにすることだけである。
- 範囲は運用の係が指定できない。本人が画面で選ぶ。
- 同じ口で、表に無い宛先の名前の一覧も頼める。これは 1 つの承認待ちになり、本人が許せば宛先の許しになる（2026-11-12、ADR-0007 の Decision「運用の係が先に頼んだときだけ、承認待ちにして知らせる」）。
- 承認の画面に出す文は、関所がコネクタの事実（操作・対象・差分・head の SHA など）から組む。運用の係が書いた文は使わない。

### 運用の係は、自分の状態を読むだけ

- 運用の係は、自分の承認待ち、効いている許し（範囲と期限）、最近断られたものと理由を読める。最近断られたものには、名前解決で断られた名前も含む（2026-11-12、ADR-0007）。書き換えはできない。
- この口は作業環境向けの口（ADR-0002 の Decision「名前解決は関所が受け、振り分けにある名前だけに答える」の固定の名前）にだけ置く。

### 設定は、Pod を作り直さずに読み直す

- 振り分け（ADR-0002 の Decision「扱いは宛先ごとに 3 つ」）と表は、環境のリポジトリの設定（ConfigMap）として持ち、関所が変わったものを読み直す。Pod は作り直さない。
  - そのために、この設定は中身のハッシュを名前に付けない形で mount する（ハッシュを付けると、変えるたびに Pod が作り直される）。
- 変更は環境のリポジトリの PR でレビューしたものだけが入る。運用の係は PR を出せるが、マージは本人がする。
- 関所には、設定を確かめるだけの動かし方を用意する。環境のリポジトリの CI でそれを通ることを、設定の変更をマージする条件にする。
- 読み直した設定が読めない・壊れているときは、それを採らず、前に読めた設定のまま動き、そのことを記録して知らせる（ADR-0006 の Decision「指標を出し、止まったことに外から気づく」）。起動のときに読めなければ起動しない（ADR-0001 の Decision「止まったら閉じる（fail closed）」）。

### 台帳

- 台帳（許しと承認待ち）は関所の SQLite に置く。宛先の許しと、断った名前の覚えも台帳に置く（2026-11-12、ADR-0007）。関所にだけ mount する専用の volume に置き（ADR-0006 の Decision「どこに、どれだけ残すか」）、backup の対象にする。
- 台帳を読めない・書けないときは、許しが無いものとして扱い、ask の操作は通さない。

### 守る対象と、倒す向き

- 守るのは、本人が許していない操作が、表の allow 以外で通らないことと、承認を決める道がモデルに無いことである。
- 許す範囲は、表の allow と、台帳の許しの範囲に当てはまるものだけである。表の deny は許しより勝つ。
- 倒す向きは、設定が読めないときは前に読めた設定、台帳が使えないときは許しが無い側である。規則に当たらない要求は宛先の既定で、既定の無い宛先は無い。

### 本 ADR で決定しないこと

- 振り分けと表の形式、読み直しと確かめの仕組み（委譲先: 関所の設定の仕様書）。
- 要求の中身の指紋の取り方と、1 回の許しの期限の長さ（委譲先: 関所の実装の PR と関所の設定）。
- 関所の応答の印の名前と形（委譲先: 関所の API の仕様書。natsumi の側はこれで見分ける）。
- 答えの無い承認待ちをいつまで残すか、同じ要求の承認待ちをまとめるか（委譲先: 関所の実装の PR）。
- 作業環境向けの口と承認を受け付ける口の、パス・欄の名前・形式（委譲先: 関所の API の仕様書と、natsumi の ADR 0096）。
- 運用の係に渡すツールの名前と説明（委譲先: 環境のリポジトリの運用の係の設定。説明は固定の文にする）。
- 表の中身（どの操作をどの既定にするか）（委譲先: 環境のリポジトリの運用の係の配置。GitHub の最初の中身は ADR-0005）。
- 承認の画面・Web Push・モデルへの知らせ方（委譲先: natsumi の ADR 0096）。

## Consequences

- 規則に当たらない要求が断られず、本人に聞かれる。本人が許せば、その場で通る。
- 期限付きの許しで、同じことを何度も聞かれずに済む。表を変えるための PR と apply は、既定を変えたいときだけになる。
- 承認は会話の外で本人が出し、関所が台帳で確かめる。会話の ok を偽っても通らない。
- ask はすぐ返るので、作業環境の道具が承認を待って詰まらない。その代わり、運用の係は 403 を読んで（git では状態を読む口で）、答えを待ってからやり直す必要がある。
- 関所の応答に印があるので、上流の 403 と関所の 403 を、作業環境の道具も natsumi も取り違えない。
- GitHub の規則に当たらない書きが全部 ask になるので、最初のうちは本人に聞く回数が多い。
- 読むだけの宛先は method で読みに限るだけで、path は絞らない。今の中継より広い path が読める。
- 生の操作の許しは宛先・method・path でしか効かないので、育てるには規則に名前を付ける PR が要る。
- 設定をハッシュ無しで mount するので、設定の変更が Pod の作り直しという分かりやすい印を残さない。いつ変わったかは、関所の記録と環境のリポジトリの履歴で追う。壊れた設定は CI で止め、すり抜けたものは読み直しの失敗の知らせで気づく。
- 期限の無い許しは取り消すまで効き続ける。棚卸しは本人の画面に頼る。
- deny を表のデータにしたので、床は関所ではなく外の仕組み（RBAC、GitHub の権限）にある。表を誤って緩めても、外の床は残る。

## Alternatives Considered

- **表に無い操作は断る（今の許可リストと同じ）**: 本人が「その場だけ」通す道が無く、許すたびに PR と apply が要る今の困りごとが残る。
- **関所のコードに「いつも断る」操作を置く**: その場だけ通したいときに、コードの変更とリリースが要る。断る操作も表のデータにし、本当の床は外の仕組みに持たせる。
- **ask の間、接続を開けたまま待つ**: 道具の時間切れに当たり、作業環境のコマンドが本人の答えまで止まる。
- **答えを運用の係に poll させる**: モデルが問い合わせのたびにターンを使う。答えは natsumi の知らせの仕組みで届ける。
- **許しの範囲に「この用件だけ」を入れる（Muse の形）**: 用件はモデルの申告で決まり、乗っ取られたモデルは用件を偽れる。
- **「ずっと」を期限付きと別の範囲にし、よく使う許しを表の既定に上げる提案を関所が出す**: 期限の無い許しと表の allow は同じ「操作 × 対象」で引くもので、違いは誰が書くかだけである。提案の仕組みが 3 つ目になり、最初の版には要らない。
- **先に頼むときに、範囲もモデルが組めるようにする**: 広い範囲を 1 押しで通させる道になる。
- **範囲の値（期限の選択肢）を natsumi の画面にも持つ**: 期限を変えるたびに 2 つのリポジトリを直すことになる。
- **表を ConfigMap のハッシュ付きで mount し、変えたら Pod を作り直す**: 作り直しのたびに作業環境の状態とターンを失う。
