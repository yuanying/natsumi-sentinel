# 0004. 操作の表で決め、表に無いものは本人に聞き、範囲付きの許しを台帳に残す

- Date: 2026-11-09
- Status: Accepted

## Context

今の運用の係（クラスタの運用を受け持つ natsumi のインスタンス）の出口の判定は、中継のスクリプトの許可リストである。結果は「通す」と「403」だけで、次のことが起きている。

- 許可リストに無い操作は断られる。本人が「その場だけやってほしい」と思っても、通す道は許可リストを書き換えることしかない。
- 許可リストを書き換えるには、環境のリポジトリの PR・テスト・apply が要り、中継の設定が変わるので Pod も作り直される。
- natsumi にある本人の承認は、Slack への投稿の承認（natsumi の ADR 0041）だけで、1 件ずつで範囲が無い。運用の係のマージの ok は会話の中で取っていて、中継は確かめられない。

関所（ADR-0001）は、ここに「聞く」と「許しを覚える」を足す。ここで使う言葉は次のとおりである。

- **操作**: 要求を、人が読める意味に揃えたもの。名前と対象を持つ（例: GitHub の PR のマージ、対象はリポジトリと PR の番号）。要求を操作に揃えるのは宛先ごとの **コネクタ** で、GitHub のコネクタは ADR-0005 が決める。
- **表**: 操作ごとの既定（allow・ask・deny）。
- **承認待ち**: ask になった要求。本人の答えを待つ。
- **許し**: 本人が承認待ちに答えて出したもの。範囲（下の節）を持ち、**台帳** に残る。

## Decision

### 操作ごとに、表で allow・ask・deny を決める

- inspect の宛先（ADR-0002）の要求は、コネクタが操作に揃え、表で決める。
  - allow: 通す。
  - ask: 承認待ちにする（下の節）。台帳に当てはまる許しがあれば通す。
  - deny: 断る。
- **表に無い操作は ask にする。** 断らずに本人に聞き、許しで育てる。
- **deny も表のデータである。** 関所のコードに「いつも断る」操作を置かない。断っている操作も、環境のリポジトリの変更で ask や allow に変えられる。
  - deny の操作は、承認の画面からは通せない。その場だけ通したいなら、本人が自分で操作するか、表を ask に変える。
  - deny で断るときは、本文に「表で断っている。変えるには本人が表を直す」ことを書く。
- 最初の版のコネクタと、操作の揃え方の粗さは次のとおりである。

| 宛先 | 扱い | 操作 |
| --- | --- | --- |
| GitHub の API と git | inspect | ADR-0005 |
| 外の係（A2A のエージェント） | inspect | 係への送信を 1 つの操作にし、対象は係の名前。既定は allow（記録だけ）で、係ごとに表で ask に変えられる |
| Kubernetes の API | inject | 揃えない。許す範囲は ServiceAccount の RBAC が決め、関所は鍵と記録だけを受け持つ |
| 読むだけの API（gated の後ろの一覧の API など）・鍵の要らない置き場 | inject | 揃えない |

- Kubernetes の API を操作に揃えないのは、許す範囲を RBAC で書けるからである。RBAC で書けない操作（多くの要求で 1 つの意味になるもの）が要るようになったら、そのときにコネクタか専用の操作を足す。

### 表・振り分け・操作の定義は、Pod を作り直さずに読み直す

- 表、振り分け（ADR-0002）、操作の定義（ADR-0005）は、環境のリポジトリの設定（ConfigMap）として持ち、関所が変わったものを読み直す。Pod は作り直さない。
  - そのために、この設定は中身のハッシュを名前に付けない形で mount する（ハッシュを付けると、変えるたびに Pod が作り直される）。
- 変更は環境のリポジトリの PR でレビューしたものだけが入る。運用の係は PR を出せるが、マージは本人がする。
- 読み直した設定が読めない・壊れているときは、それを採らず、前に読めた設定のまま動き、そのことを記録して指標に出す（ADR-0006）。起動のときに読めなければ起動しない（ADR-0001）。

### 許しの範囲は「1 回」「期限付き」「ずっと」の 3 つ

- **1 回**: 承認待ちになった要求の中身の指紋（method・path・本文や、操作の対象と引数）に 1 度だけ当てはまる。使ったら消える。
- **期限付き**: 1 時間・1 日・30 日。範囲は「操作 × 対象（リポジトリ・名前空間・node など）」。
- **ずっと**: 期限付きと同じ範囲で、期限が無い。
- 範囲は、操作の種類で絞らない。どの操作にも 3 つを出せる。危ない操作は表の既定が deny なので、範囲が効くのは本人が ask にした操作だけである。
- session と「この用件」（きっかけのアラートや PR）の範囲は入れない。用件はモデルの申告で、偽れるためである。
- 効いている許しは、本人が承認の画面で一覧し、取り消せる。期限が切れたか取り消したら、台帳から消える。
- よく使われる許しは、表の既定に上げることを関所が本人に提案する。上げるかどうかは本人が環境のリポジトリで決める。

### ask はすぐ 403 で返し、答えは会話の外から届ける

- ask の要求は、接続を開けたまま待たない。すぐに 403 で返し、本文に承認待ちの id・操作・「許されたら同じ要求をやり直して」を書く。
- 本人の答えは、server の窓口（ADR-0001 の Decision「承認を決められるのは本人だけで、会話の外で取る」の口）から関所に届く。関所は答えが出たことを server に知らせ、server がモデルに知らせる（知らせ方は natsumi の ADR）。
- 運用の係が同じ要求をやり直すと、台帳の許しに当たって通る。

### 先に承認を頼める。決めるのは本人

- 運用の係は、要求を出す前に、承認を頼める。1 つの承認待ちに、複数の対象（マージする PR の一覧など）や範囲をまとめられる。
- 頼めるのは「承認待ちを作る」ことだけで、許すかどうかは本人が決める。
- 承認の画面に出す文は、関所がコネクタの事実（操作・対象・差分・head の SHA など）から組む。運用の係が書いた文は使わない。

### 運用の係は、自分の状態を読むだけ

- 運用の係は、自分の承認待ち、効いている許し（範囲と期限）、最近断られたものと理由を読める。書き換えはできない。
- この口は作業環境向けの口（ADR-0002）にだけ置く。

### 台帳

- 台帳（許しと承認待ち）は関所の SQLite に置く。Pod の永続ボリュームの関所だけが mount する場所に置き、backup の対象にする。
- 台帳を読めない・書けないときは、許しが無いものとして扱い、ask の操作は通さない。

### 守る対象と、倒す向き

- 守るのは、本人が許していない操作が、表の allow 以外で通らないことと、承認を決める道がモデルに無いことである。
- 許す範囲は、表の allow と、台帳の許しの範囲に当てはまるものだけである。
- 倒す向きは、設定が読めないときは前に読めた設定、台帳が使えないときは許しが無い側である。表に無い操作は ask で、通す側には倒さない。

### 本 ADR で決定しないこと

- 表・振り分け・操作の定義の形式と、読み直しの仕組み（委譲先: 関所の設定の仕様書）。
- 要求の中身の指紋の取り方（委譲先: 関所の実装の PR）。
- 答えの無い承認待ちをいつまで残すか、同じ要求の承認待ちをまとめるか（委譲先: 関所の実装の PR）。
- 表の既定に上げる提案の出し方（委譲先: 関所の実装の PR。上げるのは本人の環境のリポジトリの変更）。
- 作業環境向けの口と承認を受け付ける口の、パス・欄の名前・形式（委譲先: 関所の API の仕様書と、natsumi の ADR）。
- 運用の係に渡すツールの名前と説明（委譲先: 環境のリポジトリの運用の係の設定。説明は固定の文にする）。
- 表の中身（どの操作をどの既定にするか）（委譲先: 環境のリポジトリの運用の係の配置。GitHub の最初の中身は ADR-0005）。
- 承認の画面・Web Push・モデルへの知らせ方（委譲先: natsumi の ADR）。

## Consequences

- 表に無い操作が断られず、本人に聞かれる。本人が許せば、その場で通る。
- 範囲付きの許しで、同じことを何度も聞かれずに済む。表を変えるための PR と apply は、既定を変えたいときだけになる。
- 承認は会話の外で本人が出し、関所が台帳で確かめる。会話の ok を偽っても通らない。
- ask はすぐ返るので、作業環境の道具が承認を待って詰まらない。その代わり、運用の係は 403 を読んで、答えを待ってからやり直す必要がある。やり直さなければ、許しは使われずに残る。
- 表に無い操作が全部 ask になるので、最初のうちは本人に聞く回数が多い。
- 設定をハッシュ無しで mount するので、設定の変更が Pod の作り直しという分かりやすい印を残さない。いつ変わったかは、関所の記録と環境のリポジトリの履歴で追う。
- 「ずっと」の許しは取り消すまで効き続ける。棚卸しは本人の画面に頼る。
- deny を表のデータにしたので、床は関所ではなく外の仕組み（RBAC、GitHub の権限）にある。表を誤って緩めても、外の床は残る。

## Alternatives Considered

- **表に無い操作は断る（今の許可リストと同じ）**: 本人が「その場だけ」通す道が無く、許すたびに PR と apply が要る今の困りごとが残る。
- **関所のコードに「いつも断る」操作を置く**: その場だけ通したいときに、コードの変更とリリースが要る。断る操作も表のデータにし、本当の床は外の仕組みに持たせる。
- **ask の間、接続を開けたまま待つ**: 道具の時間切れに当たり、作業環境のコマンドが本人の答えまで止まる。
- **答えを運用の係に poll させる**: モデルが問い合わせのたびにターンを使う。答えは natsumi の知らせの仕組みで届ける。
- **許しの範囲に「この用件だけ」を入れる（Muse の形）**: 用件はモデルの申告で決まり、乗っ取られたモデルは用件を偽れる。
- **操作の種類ごとに出せる範囲を絞る**: 範囲の決まりが操作ごとに増え、本人が何を許したかを追いにくい。危ない操作は既定が deny なので、要るようになったら表に欄を足せば足りる。
- **表を ConfigMap のハッシュ付きで mount し、変えたら Pod を作り直す**: 作り直しのたびに作業環境の状態とターンを失う。
